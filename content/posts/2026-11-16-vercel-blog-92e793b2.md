Agents are now users of software, doing work on people's behalf. Whether you're building the agent or the software it uses (API, CLI, MCP server, SDK), evals give you a way to measure how well that work gets done.

Agents probably missed your launch video and billboard on Highway 101, but they still go through the same funnel a human does to find and use a product:Discovery,Selection,Access, andSuccess.

You can build evals for any stage of this funnel. Here, we’ll focus on the final stage,Success: whether the agent completes the user’s task correctly.

That's more difficult to check than it sounds. An agent can place a “successful” order for a hot latte when the user asked for an iced one. The request worked, so the logs in your Observability stack look fine. And because LLM outputs vary between runs, one good manual test can’t tell you whether a fix worked. You need to repeat the same tasks and grade the outcomes, before and after the change.

That’s what an eval is, a test you run many times and score. Here’s how we build one.

## Copy link to headingThe agentic testing pyramid

If a test asks “did it work?”, an eval asks “how often does it work, and how well?”

We group agentic software tests by how many LLM calls they typically need: deterministic tests (0), one-turn evals (1), and E2E evals (2+ across a whole task). This has turned out to be a great proxy for the effort to build them, the time they take to run, and the cost of running them. Just like inthe practical test pyramid, the cheap and fast tests should make up the bulk of your test suite.

To use the pyramid, start with the problem you want to catch and pick the lowest tier that can catch it. ForSuccess, that's the top. A one-turn eval checks a single decision, like which command the agent runs first. ButSuccessdepends on the whole sequence of steps (e.g. search for cafes → filter on user criteria → place the latte order). Each one can look reasonable on its own, and the agent can still get the wrong outcome.

An E2E eval lets the agent work through the whole task in an environment, then checks whether the final result meets the user’s requirements. You’ve probably seen a few already; most popular coding benchmarks, likeSWE-benchandTerminal-Bench, are E2E evals.

## Copy link to headingHow to build an end-to-end eval

We’ll build the coffee eval withHarbor, an open-source framework from the creators of Terminal-Bench that runs agents in containers, checks results, and records their actions.

Here are the terms we’ll use:

- Task: one problem for the agent to solve, with a starting environment and a way to check whether it succeeded
- Variant: the agent setup you’re testing, like the model, prompt, tools, memory and skills
- Trial: one attempt by one variant at one task
- Run(ajobin Harbor): every variant tried on every task, several times each
- Trace(atrajectoryin Harbor): everything recorded during a trial: messages, tool calls, logs, files and final output

### Copy link to headingStep 3: Design the task set

In Step 1, we set a goal for the eval: increase how often agents order the exact drink the user asked for. But an agent can’t attempt a goal. It needs a task: one concrete request, drawn from what your users actually ask for.

Pick tasks hard enough that you learn something from running them. A good set covers the common case, the edge cases that trip agents up, and at least one request where the right move is not to act.

For each task, define these parts:

- An instruction:the user’s request
- An environment:where the agent works, with the same starting state for every trial
- A verifier:a check of the final state, ideally scored per constraint
- A known-good solution (optional):a reference run that demonstrates the expected behavior and passes the verifier

An instruction:the user’s request

An environment:where the agent works, with the same starting state for every trial

A verifier:a check of the final state, ideally scored per constraint

A known-good solution (optional):a reference run that demonstrates the expected behavior and passes the verifier

You can make every aspect of that environment as fake or as realistic as you need, depending on your goals. The OpenPipe teamhas a nice writeupon how they defined the environment for an email research agent.

We wrote four tasks, each one a Harbor task folder intasks/.

- Don’t act:impossible-request, where nothing fits, so the right move is to tell the user

#### Copy link to headingAutomated trace analysis

For larger runs, inspecting every trial by hand gets slow, so we automate it.

Up to 40 reader agents running fast models likedeepseek/deepseek-v4.1-flashread trial transcripts in parallel and summarize their findings. A smarter coordinator agent reviews those summaries, sends readers back for more context when needed, and writes the final report. Ananalysis.mdfile tells the coordinator what to look for, so we can reuse the workflow across runs.

Model calls go throughAI Gateway. Trial artifacts stay inVercel Drivesduring analysis, and traces go toVercel Blobfor long-term storage.

## Copy link to headingIterate to greatness

Your first eval run gives you a baseline. Now act on it.

Pick the fix the traces point to, like the--max-totalflag, rerun the same job, and compare against the baseline. Check whether it reduces the targeted failures without introducing new ones, then use those results to decide whether the change is ready to ship.

Once you’ve built an eval, it keeps paying off for a lot of different things. Rerun it on every release to catch regressions; test prompt, skill, and model changes before shipping; learn how agents use your product; or build auto-optimization loops on top of it.

Expect to add harder tasks over time. As models and your product improve, evals saturate, meaning agents start passing every task.A saturated eval still catches regressions, but it can’t tell you what to improve next.

Evals are the infrastructure you use tomake your product better, again and again. Vercel has the pieces you need to build them in one place:AI Gatewayfor model calls across providers,Sandboxto run trials at scale, andDrivesandBlobto keep every trace.
