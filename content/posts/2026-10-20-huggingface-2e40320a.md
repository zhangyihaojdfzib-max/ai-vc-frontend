# MPS in PyTorch 2.15

If you run models on your Mac or use MPS as your primary acceleration tool for computing, there's plenty to look forward to in PyTorch 2.15! FP8 arrives on MPS, language-model decoding gets faster paths through linear layers and softmax and new Metal kernels tackle some surprisingly expensive parts of audio, video and training workloads.

A quick word about who we are: we're the PyTorch team at Hugging Face. We contribute across PyTorch, and one of our focus areas is the MPS backend, where the goal is to make your Mac a first-class place to run and train PyTorch models. At the start of 2026, running even small models on MPS often meant working around unsupported operations, performance cliffs and unexpected memory growth. So we run real models from the Hugging Face Hub across language, image and video, find where MPS falls short and fix it upstream in PyTorch, more and more often by replacing MPSGraph with dedicated Metal kernels. Much of this post is the result of that work, done together with the PyTorch maintainers and community contributors.

## TL;DR

- FP8 comes to the Mac:storefloat8_e4m3fnvalues in half the space of BF16 and use scaled matrix multiplication and all other ops which are supported on CUDA/CPU!
- MoE models decode 5–6.5× faster than in 2.14:Qwen3.6-35B-A3B goes from 9.4 to 61.3 tokens/s on an M3 Ultra, thanks to a native grouped matmul with a dedicated decoding path, fewer GPU-CPU syncs and faster top-k routing.
- Less time per token for every LLM:single-row linear layers use specialized matrix-vector kernels, and softmax over the vocabulary is about 8× faster.
- More linear algebra on the GPU:complex LU and triangular solves, faster small-matrix inverses, and faster QR decomposition.
- Audio, video, and training get attention too:faster paths for convolutions, padding, dropout, interpolation backward and reductions. Wan2.2's video VAE decode now peaks at 8 GiB of memory instead of 270 GiB.
- More control from Python:public MPS streams and more reliable event timing.
- Updated requirements:MPS now requiresmacOS 15 or later; PyTorch 2.15 requiresPython 3.11 or later.
- A peek at 2.16:attention fully on Metal, more MPSGraph-to-Metal migrations and faster LLM decoding.

## FP8 comes to MPS

FP8 gives you another way to save memory on your Mac. PyTorch 2.15 addstorch.float8_e4m3fntensors on MPS: one byte per value, half the storage of FP16 or BF16.

You can multiply these tensors withF.scaled_mm, which supports both tensorwise and rowwise scaling. Here's a small example with one scale per tensor:

```python
import torch
import torch.nn.functional as F

def quantize_fp8(x):
    limit = torch.finfo(torch.float8_e4m3fn).max
    scale = x.abs().amax().clamp_min(1e-12) / limit
    return (x / scale).to(torch.float8_e4m3fn), scale

x = torch.randn(1, 1024, device="mps", dtype=torch.float32)
weight = torch.randn(1024, 1024, device="mps", dtype=torch.float32)
x_fp8, x_scale = quantize_fp8(x)
w_fp8, w_scale = quantize_fp8(weight)

y = F.scaled_mm(
    x_fp8,
    w_fp8.t(),
    scale_a=x_scale,
    scale_recipe_a=F.ScalingType.TensorWise,
    scale_b=w_scale,
    scale_recipe_b=F.ScalingType.TensorWise,
    output_dtype=torch.bfloat16,
)
print(y.shape, y.dtype)

```

## Faster language-model decoding

Every LLM has a prefill phase and a decode phase. During decode, each new token goes through the model as a single row, so the big matrix multiplications turn into matrix-vector products. PyTorch 2.15 speeds up both kinds of layers that dominate this step: dense linear layers and mixture-of-experts layers.

### Linear layers

MPS has had GEMV kernels fortorch.mmsince 2.14, butF.linearstill went through MPSGraph. PyTorch 2.15connects them toF.linear, so the common[1, 1, hidden_size]decoding input uses them directly, with eligible bias additions fused in. Across 96 BF16 layer shapes from real models, that's a1.23× geometric-mean speedup. The biggest wins land on small projections, such as the gates in MoE models, where the old path left most of the memory bandwidth unused. Large layers and LM heads were already close to bandwidth-bound, so they stay near 1×.

### Mixture-of-experts layers

A mixture-of-experts layer sends different numbers of tokens to each expert. Grouped matmul handles those uneven groups in a single operation, and 2.15 gives MPS anative implementation.

In 2.14, grouped matmul copied the group offsets to the CPU and looped over the groups. The new Metal kernels read the offsets directly on the GPU, using Metal Performance Primitives where available and a separate Metal path elsewhere. Small groups, the common case during decoding, gettheir own kernelas well.

For example, 64 tokens can be split into groups of 16, 32, and 16:

```python
import torch
import torch.nn.functional as F

tokens = torch.randn(64, 64, device="mps", dtype=torch.bfloat16)
weights = torch.randn(3, 128, 64, device="mps", dtype=torch.bfloat16)
ends = torch.tensor([16, 48, 64], device="mps", dtype=torch.int32)

out = F.grouped_mm(tokens, weights.transpose(-2, -1), offs=ends)
print(out.shape)  

```

The decoding kernel shows up directly in token throughput. On anM3 Ultra withtorch.compile, MoE models generate about1.3× more tokens per second:

## Linear algebra gets a boost

### Complex-valued computations

Working with complex tensors gets easier.complex64LU factorization,LU solveandtriangular solvenow run on MPS, which also unlocks the operations and gradients built on them, such as complex determinants. Here's a small system solved directly on the GPU:

```python
import torch

a = torch.randn(8, 8, device="mps", dtype=torch.complex64)
a = a + 8 * torch.eye(8, device="mps", dtype=torch.complex64)
b = torch.randn(8, 2, device="mps", dtype=torch.complex64)

lu, pivots = torch.linalg.lu_factor(a)
x = torch.linalg.lu_solve(lu, pivots, b)
print((a @ x - b).abs().max().item())

```

## More control with MPS streams

You can now pick which MPS stream runs your work, directly from Python.torch.mps.Streamand thetorch.mps.streamcontext managerprovide the interface, andTensor.record_streamlets the allocator track a tensor's use on another stream.

Here's a small example that sends work to a separate stream and synchronizes before reading the result:

```python
import torch

x = torch.randn(1024, device="mps")
torch.mps.synchronize()
worker = torch.mps.Stream()

with torch.mps.stream(worker):
    y = x.square()
    x.record_stream(worker)

del x
worker.synchronize()
print(y.cpu().shape)

```

Work on 2.16 is already well underway. Some of the changes below have landed onmainand are available in the nightlies; others are still in review, so details may change before the release.

### Attention runs entirely on Metal

Scaled dot-product attention isdropping MPSGraph completely: every shape will run on Metal kernels, with dedicated vector kernels for decoding and Metal Performance Primitives for half-precision prefill on newer macOS versions. The shapes that used to fall back to MPSGraph benefit the most. On an M5 Pro, decoding with grouped-query attention (32 query heads, 8 KV heads, head dim 80, 4K context) drops from 465 µs to 65 µs, and a 4K × 4K prefill with head dim 40 goes from 42 ms to 6 ms.

### More MPSGraph to Metal migrations

The move away from MPSGraph continues. Batch normforwardandbackwardare in progress, whileMSE loss(up to 12× faster on small inputs),std_meanandvar_mean(up to 4× faster) andbincounthave already landed.bincountis the most dramatic: when most values fall into a single bin, counting 4 million integers used to take 6.8 seconds and now takes half a millisecond.

### A smaller install

Bundled shaders willbuild for Metal 3.1 by default, with Metal 4 versions compiled only for the kernels that need them. That shrinkslibtorch_cpu.dylibby about 25%, from 384 MiB to 287 MiB, and lays the groundwork for Metal 4.1 shaders with faster matmuls and native FP8 matrix multiplication.
