• 将 Genie Agents 扎根于结构化数据（托管表、外部表、外发表、视图、指标视图和物化视图）和非结构化文件（Unity Catalog Volumes）中，使一个 Agent 能够跨所有这些数据源进行回答。• Agent 治理位于 Catalog 层，而非模型层。治理随 Agent 扩展，而不会失控。• 借助 Unity Catalog 中的自动身份管理（AIM）、对象权限、ABAC、行过滤器和列掩码，Genie Agents 以用户身份运行，每个答案都根据该用户的权限进行过滤。

构建一个自动化简单业务任务的 Agent 可能很容易。但创建一个真正理解你的业务并尊重你现有数据治理的 Agent 则困难得多。

长期以来，团队不得不使用独立的系统来分析结构化和非结构化数据，往往花费数周时间仅仅为了打通两者。通过支持直接从表和非结构化文件中进行分析，Genie Agents 简化了这一架构，使你能够用结构化和非结构化数据同时扎根于一个 Agent。

当你整合这些数据时，一个关键问题浮现：如果一个 Agent 能访问所有数据，是什么阻止它把错误的信息告诉错误的人？

好消息是，借助 Databricks，答案存在于你已有的数据治理基础之中。你今天所依赖的同一套 Unity Catalog 机制（身份同步、对象权限、ABAC、行过滤器和列掩码）会自动治理 Genie Agents，无需任何额外设置。这种无缝继承依赖于精心设计的治理策略，我们将在下文详细探讨。

为了将这些概念具体化，我们将以虚构的全球砖块零售商 Brickstore 为例，逐步演示这些场景。

## 治理契约：Genie Agents 以最终用户的凭据运行

核心架构原则很简单：Genie Agents 以最终用户的凭据运行。Unity Catalog 默认强制执行治理，确保对表和卷的访问直接与最终用户现有的身份和权限绑定。

这一点至关重要，因为许多自建系统授予 Agent 广泛访问权限，并依赖提示词工程在模型层过滤结果。这实际上让 LLM 成为你的安全边界——这是一个危险的赌注，因为模型可能被操纵或绕过。告诉审计人员“我添加了指令说不显示受限数据”并不是一个站得住脚的治理控制措施。

借助本文概述的治理框架，Unity Catalog（而非模型）仍然是你的安全边界，就像它在 Databricks 其他部分一样。虽然 Genie 决定如何查询数据，但它无法返回最终用户无权查看的记录，因为每个答案在离开 Lakehouse 之前都会在数据层进行过滤。

## 第 0 步：从身份开始：自动身份管理（AIM）和即时（JIT）配置

架构基础始于确保你的企业身份既准确又最新。

访问控制从根本上说，其可靠性取决于其所评估的身份。如果 Databricks 中的组成员关系是你身份提供者中内容的过时手工副本，那么“brickstore_apac 成员只能查看 APAC 订单”这样的策略就毫无意义。

适用于 Microsoft Entra ID 和 Okta 的自动身份管理弥补了这一差距。启用后，用户、组、组成员关系和服务主体会自动从这些身份提供者同步到 Databricks，无需 SCIM 应用。即时配置始终开启，因此从未登录过 Databricks 的用户在首次登录时即被配置，并已携带其现有的组成员关系。

流程如下：

1. IdP 是事实来源。某人加入 APAC 销售组织；你的身份提供者将其放入 brickstore_apac 组。
2. AIM 将其同步到 Databricks——包括组成员关系。JIT 在用户首次打开 Genie One 时在 Databricks 上配置该用户。
3. Unity Catalog 策略以这些组为关键依据——对象权限、ABAC 策略、行过滤器和列掩码都在查询时评估组成员关系。
4. 用户向 Genie Agent 提问，答案完全由其组权限所允许的范围决定。不多不少。

其回报在于治理是持续性的，而非一次性设置。当员工从 APAC 调往 AMER 时，IdP 将其在组间移动，同步传播该变更，他们下一次向 Genie 提问时返回的就是 AMER 视图——无需任何人提交工单或对 Genie Agent 进行更改。当员工离职时，他们会在 IdP 中被停用，其对所有 Genie Agent 的访问权限也会立即被移除。

## 第 1 步：扎根结构化数据并控制四层访问

一旦身份被正确建立，我们现在可以关注他们被允许看到什么。对于结构化数据，Genie Agent 可以访问任何 Unity Catalog 数据资产——表、视图、物化视图、指标视图、流式表，甚至从外部系统联邦的外部表。

例如，Delta 表是事实和维度。在 Brickstore 中，即 brickstore.sales.orders（每笔订单，包含 region 和 customer_email）和 brickstore.sales.products（砖块目录）。指标视图是之上的受治理语义层——它们以 YAML 格式一次性编码你的业务指标定义（例如“净收入”的含义、“砖块销量”如何计算、什么算作“畅销砖块”），使每个消费者以相同方式计算它们。

在这些资产之上是四层访问控制，人们经常将它们混为一谈：

| 层 | 它回答的问题 | 机制 |
|---|---|---|
| 对象权限 | 谁对什么资源拥有什么级别的访问权限？ | 在 Catalog/Schema/表上授予 SELECT |
| 基于属性的访问控制（ABAC） | 哪个策略适用，适用于什么？ | 受治理标签驱动的策略，一次附加并传播（例如：任何带有“PII”标签的列仅对某些组可用） |
| 行过滤器 | 用户有权访问哪些行？ | 在查询时评估每一行的 SQL 用户定义函数（UDF）（函数返回 FALSE 的行将从查询结果中排除） |
| 列掩码 | 哪些列应被掩码以及如何掩码？ | 以列值作为输入并返回原始值或掩码版本的 SQL UDF |

对象权限是第一层访问控制：没有 SELECT 权限，Genie 无法代表最终用户查询表。但授予对表的访问权限并不意味着你需要授予全部权限。你可以在这些授权之上叠加行过滤器和列掩码，因此区域经理可以查询订单表，但只能看到自己区域的行，且永远看不到原始客户电子邮件。这些行和列控制所依据的组与你授权时使用的组相同——is_account_group_member('brickstore_apac') 等。接下来要讲的 ABAC 并不会取代这些；它只是通过策略而非逐表附加相同过滤器和掩码的一种方式。

### ABAC：一次定义策略，让其传播

旧的行和列安全方式是逐表进行：编写一个行过滤器，附加到 orders 表；编写一个列掩码，附加到另一个表；如此反复。这种方式仍然适用于一次性逻辑，但在数百张表中，它是一种容易出现漏洞的配置。

ABAC 策略（现已在 Unity Catalog 中与受治理标签和自动数据分类一起正式发布）颠覆了这种方式。你用受治理标签（账户级、受访问控制的键值对，如 pii:email）标记敏感数据，然后编写一个策略，声明“无论此标签出现在哪里，都应用此保护”。新表在被打上标签的那一刻就继承了保护，因此无需逐表操作。

## 第 2 步：将相同的治理扩展到文档

从历史上看，在处理非结构化数据时，团队的治理策略一直更具挑战性。虽然结构化数据在数据仓库或数据库中得到了安全管理，但文档通常保存在由独立 ACL 管理的隔离存储系统中。

解决方案是将文件置于与结构化数据相同的治理平面内。您可以将它们放入 Unity Catalog Volumes，它们就会像其他所有对象一样成为可保护对象。您向应查看这些卷的组和用户授予 READ VOLUME 权限，Genie 会在相同的身份契约下基于这些文档进行推理：

在设计您的 Agent 之前，有一个行为值得理解：当您将卷附加到 Genie Agent 时，它将成为必需的数据源。这意味着 Agent 在加载时会验证对每个附加源的访问权限，因此对附加卷缺乏 READ VOLUME 权限的用户将完全无法使用该 Agent。换句话说，卷的授权是使用 Agent 的先决条件，因此请确保将每个 Agent 的文档源范围限定为应使用该 Agent 的受众。如果两个受众需要不同的文档，您可能需要为他们提供不同的 Genie Agent（每个 Agent 仅挂载该用户可读的卷）。

另请注意，Unity Catalog Volume 是最小的可保护单元，因此权限适用于整个卷，而非单个文件。您不能选择共享特定文件；您必须授予对整个卷的访问权限，或者完全不授予。

考虑到这些注意事项，卷可以直接作为知识源附加到 Genie Agent，方式与附加表或视图相同。Genie Agent 的读取能力远不止 PDF——支持的格式包括 PDF、图像文件（JPG、JPEG、PNG、TIFF、TIF）以及 Office 文档（DOC、DOCX、PPT、PPTX），还有纯文本和 Markdown。实际上，这意味着扫描的合同、幻灯片和规格表都可以处理，而不仅仅是规范的 PDF。（完整列表和当前限制请参阅 Genie Agents volumes 文档。）

为确保准确路由和最佳性能，请遵循以下配置卷的最佳实践：

- **添加清晰的描述**：准确描述卷中包含的内容、组织方式以及 Agent 应如何使用它。不要使用通用占位符。例如，不要使用“区域文件”，而应使用“APAC 市场报告——APAC 区域的需求驱动因素、趋势和关注事项”。Genie 依赖此描述来选择正确的卷。
- **避免重复内容**：附加包含重叠信息的多个卷会使 Agent 更难检索相关文档。卷内的单个文件也是如此。
- **避免无关文件**：仅包含与 Agent 领域相关的文件。无关文件可能会混淆 Agent。
- **使用清晰的文件名**：使用描述性文件名，以便 Agent 区分文件。

- **结构化数据，由非结构化知识增强**。如果没有区域文档，Genie 可能能够轻松回答“是什么”的问题，但很难弄清楚是什么因素在推动需求。有了非结构化数据，Genie 就能全面了解业务背景。

## 值得关注的模式

当您将本文的经验应用到生产环境时，有几个模式值得关注：

- **先打标签，再定策略。不要逐表掩码。** 直觉是保护您面前的三张表。请抵制这种冲动。定义受治理的标签和 ABAC 策略，以面向未来地保障您的数据治理。
- **每个卷对应一个受众。** 由于卷是最小的授权单元，请在卷的边界处决定文档访问权限。如果两个文档需要不同的读者，它们需要不同的卷和不同的 Genie Agent——请提前规划布局。
- **通过 MCP 或 API 对外暴露 Genie One 或 Genie Agents 时要小心**——您必须谨慎处理身份问题。与通过 Databricks UI 运行不同，您并不总能使用最终用户的身份（例如，使用 Service Principal 进行认证时）。有特定的模式需要采用，Databricks 在 Access Genie everywhere 中详细说明了 U2M、M2M 和 OBO 配置。
- **通过模拟测试，而非检查。** 不要通过阅读策略并说服自己它是正确的来验证治理——以每个组的成员身份提出相同的问题并比较响应。将其作为回归测试，并在策略或组成员身份发生变化时运行它。

## 要点总结

构建一个 Agent 可能很容易，但对其进行治理需要真正的设计工作。在 Databricks 中，企业身份从 IdP 同步，对象权限控制访问，ABAC 和受治理的标签提供规模化保护，行过滤器和列掩码控制返回的内容，文档与数据保存在同一系统中。

通过这种设置，Genie Agents 无需任何额外配置即可继承所有治理。
