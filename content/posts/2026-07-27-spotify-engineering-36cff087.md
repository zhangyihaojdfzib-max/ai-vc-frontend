# 为在线点查询索引数据湖

![特色图片](/images/posts/d2704bae42e9.png)

像Spotify这样的公司需要大量数据以低延迟方式供在线服务访问，并且越来越多地需要供代表用户行动的AI Agent（智能体）使用。在线服务——例如使用或显示用户收听历史的门户和个性化功能——需要以交互速度查找和分页浏览每个用户的数据。AI Agent（智能体）回答诸如"去年夏天我在听什么？"之类的问题时，需要快速检索用户数据，以便对其进行推理——过滤、聚合，甚至本地运行SQL——为LLM（大语言模型）提示词构建上下文。这两种模式共享相同的基础原语：通过键对数据集进行快速点查询，而这些数据集通常过于庞大，无法经济地常驻在Bigtable或DynamoDB等键值（KV）存储中。

在Spotify，PB级数据驻留在Bigtable中用于在线用例——但EB级数据存储在GCS数据湖中。数据湖的底层存储速度很快且越来越快——GCS每次请求提供30-100毫秒延迟，而S3 Express One Zone和GCS Rapid Storage现在提供个位数毫秒延迟。瓶颈越来越不在于存储层本身，而在于上层的查询引擎：像Trino和BigQuery这样的分布式SQL引擎即使对于单行查找也会增加数秒的作业调度和查询规划开销。它们是为分析吞吐量而设计的，而非交互式点查询。

随机访问Parquet（RAP）弥合了这一差距。外部索引将键直接映射到文件位置，精确的范围读取仅获取所需的字节。RAP操作于已由机器学习流水线、笔记本、实验平台和批量分析共享的相同Parquet文件——一次存储、一次付费，而非在专用服务系统中维护单独的副本。

## 分布式SQL引擎如何在大海捞针

用户询问AI Agent（智能体）去年夏天他们听了什么。仅收听历史数据就跨越数十亿用户，分布在数千个大型每日文件中，而夏季大约有90天。假设每天有1,000个文件，那就是90,000个独立的Parquet文件。在在线用例的任何合理时间或计算预算内，即使读取每个文件的一小部分也是不可行的。

有标准方法可以减少候选集。在每个每日分区内，文件可以进一步按键分区——这是一种常用于加速连接的技术，当键合适时也有利于点查找。仅从文件名，引擎就能知道给定的用户ID是否可能在该文件中。每天有1,000个桶，候选集从90,000减少到90。用户ID列上的布隆过滤器可以在不打开文件的情况下丢弃文件——缓存在元数据存储中，它们将90个候选者缩小到用户实际活跃的大约12天。

我们仍然需要读取这12个文件。每个文件都很大，在其中查找一个用户的数据需要一系列依赖读取：获取页脚、解析行组元数据、扫描键列以定位匹配行，然后使用列和页面索引在每个值列中找到相应的页面。每个文件、每列都需要多次往返依赖获取到云存储——而每次往返都与其他并发查询争用IOPS。按键分区和布隆过滤器有助于选择文件，但它们不能解决文件内的问题。

## RAP方法

依赖读取链是根本瓶颈，并且适用于每个存储层级。每个环节都消耗延迟（下一次开始前的一次往返）和带宽（仅为发现下一步读取位置而读取的字节）。在云存储上，每次I/O环节消耗数十毫秒；在本地SSD上，微秒级；在内存中，纳秒级。绝对数值变化，但结构相同：每一步都依赖于前一步的结果。压缩该链——用单个预计算查找替换依赖读取——无论存储层级如何，都能节省延迟和带宽。我们通过云对象存储来说明该方法，因为每次往返的成本使收益最为显著，但该原理是通用的。

RAP不扫描，而是查找。外部索引将每个键直接映射到其数据所在的每个文件和行号。给定一个键，读取器查找索引，使用缓存的文件元数据将行号解析为页面位置，并发出范围读取以精确获取所需的页面。索引查找是O(1)，缓存的页面映射是低延迟操作，数据检索是少量精确的范围读取。重要的是，这些读取可以并行发出——没有依赖加载链。

### 外部索引

RAP可以操作于任何现有的Parquet文件，无需特殊准备。索引构建器读取将要检索的列的页脚和页面位置，扫描键列以构建键到位置的映射，并将其写出。随着新数据的到来，每次流水线运行都会产生相应的索引条目。索引通过追加片段增长，而非修改现有片段。

该索引是一个多映射——单个键可以跨多个文件和分区有条目。每个条目紧凑：

| 字段 | 描述 |
|------|------|
| 键 | 查找键（例如用户ID，可能是复合的） |
| 文件ID | 哪个Parquet文件（字典编码的序号） |
| 行号 | 该文件中的行 |
| 值计数（可选） | 值的数量，支持分页 |

根据经验，索引TB级数据产生GB级索引；索引PB级数据产生TB级索引。大型索引通过哈希分桶自然分布。

这与Parquet内置的PageIndex或布隆过滤器有根本不同：那些是概率性的，用于缩小扫描范围。外部索引是确定性的——给定一个键，它返回精确的文件和行，完全消除扫描。

在未修改的文件上，RAP读取包含目标行的整个页面——可能是一个4MB的页面来提取100字节。对于延迟或成本敏感的工作负载，写入时准备使读取更小、更精确地定位。这意味着要深入了解Parquet内部结构和数据处理流水线的细节——但这才是真正收益所在。

## 针对预准备Parquet文件的优化

外部索引改变了读取器在接触文件之前所知道的信息——所需的精确文件、行和列。以下优化适用于服务于点查询的那些列；同一文件中的其他列可以保留最适合批量分析的任何布局。许多技术本身就有用，有些对任何读取器都有益，而不仅仅是RAP。但外部索引改变了权衡的平衡：有助于文件内发现的属性（细粒度页面索引、用于谓词下推的小页面、用于下推的字典编码）变得不那么重要；最小化最终读取的属性（更少的往返、更小的获取、连续的数据）变得更加重要。

优化分为三类：集中键的数据、减少每次读取的字节数、减少读取次数。

### 集中键数据

按键排序确保同一键的所有行在每个文件中连续，将它们集中到尽可能少的页面中。许多流水线已经产生排序输出。哈希分桶（Spark、Scio SMB、Iceberg桶变换）更进一步，保证每个键确定性地映射到每个分区的一个文件。

共分组——构建模式使每个键在重复或嵌套列中出现一次并带有值，例如：`SELECT user_id, ARRAY_AGG(STRUCT(timestamp, track_uri, duration_ms)) FROM streams GROUP BY user_id` 每个文件每个键产生一行，不依赖排序顺序，并且通常是自然的。

更粗粒度的分区会减少一个键所跨越的文件数量。按天分区每年为每个键生成365个文件；按周分区则将其减少到52个——索引条目更少，并行读取更少，索引更小。这需要在批量查询的分区剪枝粒度上进行权衡。

### 减少读取的字节数

即使索引指向了确切的页面，该页面也可能远大于目标数据。

**每个键一个页面。** 写入器在键边界处刷新页面——每当键发生变化时便进行分页。整个解压后的页面都属于目标键；无需进行行提取。由于每个页面现在只属于一个键，页面位置可以直接存储在索引条目中——无需单独的页面索引。文件仍保持标准的Parquet格式。每个键边界大约会增加20字节的页头开销——当每个键有大量数据时，这可以忽略不计。在键边界处重置压缩器通常对压缩比影响不大，但这取决于数据本身。一个副作用是，如果Parquet文件包含PageIndex，其大小将随键的数量而非传统页面的数量成比例增长。

**页面内的ZSTD帧重置。** 当“每个键一个页面”会导致PageIndex膨胀时，另一种方案是保持传统页面大小，但将每个键的行数据作为页面内独立的ZSTD帧进行压缩。索引存储每个列中每个帧的字节偏移量和大小，无需单独的页面索引即可直接寻址数据。对于标准读取器来说，页面正常解压（ZSTD帧只是简单地拼接在一起）。对于RAP来说，每个帧都是独立可寻址的。其权衡在于：每个帧内的值必须能在没有前序帧的情况下被解释，这排除了增量编码和游程编码。PLAIN编码或字典编码可以满足此要求，但对于某些数据类型可能不够紧凑。对于RAP的主要用例——blob、JSON、平面值列——这通常是可以接受的。

**存储对齐。** ZSTD可跳过帧可以在键之间填充数据，以便将读取操作对齐到存储块边界（例如4KB或16KB）。跨越块边界的读取需要读取两个块。在本地磁盘上，IOPS是直接约束，对齐可以避免不必要的块读取。在云对象存储上，提供商不会按IOPS计费或限流，但底层存储仍然基于磁盘，因此对齐仍然是一个有用的微优化。填充数据量很小，文件仍然是有效的Parquet格式。

### 减少读取操作

在标准的Parquet文件中，跨N列获取一个键的值需要N次并行读取——消耗N倍的请求容量，并将每个键的延迟推向分布曲线的尾部。**减少读取次数是最大的单一收益。**

**Blob和变体类型。** 将随机访问所需的字段存储为单个列——JSON、Protobuf或Parquet变体类型——意味着每个文件只需一次读取。这与在线应用程序消费数据的方式自然一致：作为一个文档，而不是单独的字段。其权衡是，批量分析会失去blob内部的逐字段列剪枝和谓词下推能力。

**列交错。** 当需要多个列时——一些用于点查询，另一些用于批量分析——写入器可以在物理上交错排列它们。来自不同列的每个键的数据被相邻写入：键1的列A，键1的列B，键2的列A，键2的列B。ZSTD可跳过帧在列之间桥接，因此每个列仍然是一个有效的压缩流——传统读取器顺序读取列A，解压器会在跳过帧内静默地跳过列B的数据。RAP读取器会针对一个键的所有列发出单个连续的区间读取。该文件仍然是完全有效的Parquet格式。

![列交错](/images/posts/cca7c9438cc1.png)

这实际上是在不破坏向后兼容性的情况下，将选定列组的布局转换为行优先。其权衡是：读取单个交错列的传统读取器也会将其他列的数据作为死区读取，从而增加了单列扫描的I/O量。在本地存储上，这通常由操作系统缓存吸收；在云存储上，读取器需要合并重叠的读取。

列交错对于部分拆分的变体列特别有用：类型化列支持快速的矢量化分析，而将变体blob与它们放在一起，则允许RAP进行单次读取，同时为分析读取器带来最小的开销。

**覆盖索引和提升值。** 索引构建器在构建时会访问每一行。对于小值，它可以将值直接**提升**到索引条目中——这是一个覆盖索引，完全消除了存储读取，将读取次数减少到零。这可以扩展到预计算的聚合：每个键的事件计数、总播放时间、类别细分，都可以以索引查找的速度获得。提升后的值还支持在索引级别进行谓词下推——在任何存储读取之前过滤条目。

### 总结

| 优化 | 点查询收益 | 分析权衡 |
| :--- | :--- | :--- |
| 按键排序 | 每个键的文件和页面更少 | 共分组 |
| 每个键一行；自然集中 | | |
| 更粗粒度的分区 | 每个键跨时间的文件更少 | 更粗粒度的分区剪枝 |
| 每个键一个页面 | 整个页面就是结果 | 适度的PageIndex增长 |
| ZSTD帧重置 | O(1)访问，无需页面激增 | 仅PLAIN编码；文件大小适度增加 |
| Blob / 变体类型 | 每个键单列读取 | 无逐字段剪枝 |
| 列交错 | 所有列的单个连续读取 | 单列扫描的I/O增加 |
| 存储对齐 | 边界处无读取放大 | 文件大小适度增加 |
| 覆盖索引 | 完全无需存储读取 | 索引大小增加 |

综合来看，这些优化可以将一个点查询简化为一次几KB的连续区间读取——或者完全消除存储读取。

## 二级索引

一个数据集可能有多个查找维度——例如，一个按buyer_id和seller_id查询的交易数据集。RAP通过在同一组索引条目上构建多个访问结构来支持这一点，每个维度一个。哈希表提供O(1)的精确查找；排序索引支持范围查询。添加或删除二级索引是一个服务层的决策——无需更改管道，无需重写数据。

文件布局有利于数据排序所依据的那个维度。二级查找可能会分散到更多文件中，但读取器会自动合并相邻的字节范围。**空间填充曲线**，如Z序曲线和希尔伯特曲线，是互补的——它们在文件布局层面改善了二级维度的局部性，而二级索引则提供了访问路径。

## 结论

RAP的关键特性是它操作的是数据湖中已有的相同Parquet文件。BigQuery为生成每周聚合报告而扫描的文件，与AI Agent为上下文检索而读取的文件是相同的。无需复制，无需ETL，无需第二份存储账单。

这改变了哪些数据可以在线服务的经济性。如今，团队需要艰难地决定在KV存储中保留什么，因为每GB的成本迫使人们进行优先级排序。有了RAP，点查询的成本降低到了云存储读取的成本。历史数据、长尾实体、低流量特性——所有这些都变得适合交互式访问。AI Agent不必将其上下文限制在KV存储所持有的内容上；它可以跨越数月或数年，回溯整个数据湖的广度。

数据湖不再仅仅是批处理的。同一份存储服务于分析型和工作负载型两种场景——一个数据集，两种访问模式。
