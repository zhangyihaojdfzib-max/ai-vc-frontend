# Inside the Codex sandbox

How Codex runs commands on your machine with limits you control.

By Michael Bolin, Member of Technical Staff

At OpenAI, we take adefense in depth⁠(opens in a new window)approach when it comes to safeguarding agents. While our investments in training and alignment are fundamental to this effort, we also implement features in our agentic harness,Codex⁠(opens in a new window), to provide additional protections. Because one of the most common (and potentially risky) things Codex does is run commands on your computer, we built theCodex sandboxso Codex can work in your existing environment within filesystem and network limits you control.

A⁠(opens in a new window)sandbox⁠(opens in a new window)limits what a program can access while it runs. For a photo-organizing task, you might configure the Codex sandbox to let commands read and modify files in~/Pictureswhile blocking network access to prevent uploads. For code review, you might allow access to online documentation while keeping source files read-only. Users configure the Codex sandbox through⁠(opens in a new window)permission profiles⁠(opens in a new window), which define the filesystem and network restrictions for a Codex session.

In this article, we’ll start with the tradeoffs behind Codex’s sandbox defaults, then explain the sandbox’s design and how the harness uses it to run commands. We’ll show how end users and enterprises can tailor its permissions to their needs and how developers can reuse the sandbox in their own tools. Finally, we’ll examine how these restrictions are enforced on macOS, Linux, and Windows.

## Choosing the sandbox boundaries

In Codex, our philosophy is to specify conservative defaults for the sandbox that still enable meaningful work. For example, with a Git repository as the workspace root, the built-in:workspacepermission profile:

- Allows writes within the workspace, while keeping directories such as.gitand.codexread-only.This lets Codex edit source code without seeking permission for every change, while preventing direct changes to.codex/config.tomlor Git hooks under.git/hooks.
- Allows broad filesystem reads, subject to the user’s existing OS permissions.Compilers, runtimes, and build tools depend on SDKs, libraries, and configuration outside the repository. Restricting reads to the workspace would break many ordinary workflows. The tradeoff is that sensitive files elsewhere on the machine may also remain readable (such as config files containing API keys).
- Disables network access.This blocks direct uploads to external services, including attempts to exfiltrate data the command can read. It also prevents legitimate operations such as downloading dependencies, which require additional access.

These restrictions prevent a large class of bad behavior, but harmful actions are still possible. For example, the agent could inject malicious code into a locally installed package such asnode_modules/prettier. Such a change might not appear ingit statusbecausenode_modulesis often ignored by Git. If the user’s editor runs that copy of Prettier on save, simply saving a file could execute the malicious code outside the Codex sandbox. This is why we take a defense in depth approach: the sandbox limits what commands can access, while training and alignment help the model use that access in accordance with the user’s intent.

For guidance on tailoring sandbox permissions and combining them with other protections in an enterprise environment, see theCodex security cookbook⁠(opens in a new window).

## Designing the sandbox

Virtual machines andcontainers⁠(opens in a new window)are two popular mechanisms used for sandboxing, but we take a different approach with the Codex sandbox. Instead of moving computation to a separate environment to provide isolation, Codex uses each platform’s sandboxing facilities to constrain commands running in the user’s existing environment.For many developers, their laptop serves as a bespoke dev environment that they can change on a whim. Reproducing that environment in a Docker container can take work, and some workflows still depend on tools that run on the host.

For example, consider using Codex to develop an iOS app on a Mac. If you decided to sandbox Codex by running it inside Docker, Codex would not be able to run the iOS build toolchain composed of native Mac executables, nor could it launch the iPhone simulator to run the code. A Docker-based workflow could delegate builds and simulator operations to the Mac host, but those operations would execute outside the container’s sandbox and would need their own restrictions. For Codex, we prefer to keep things simple by investing heavily in OS-specific sandboxing so Codex can run in the environment that is most appropriate to the task at hand.

The harness exposes these OS-specific sandboxing mechanisms through a common API across macOS, Windows, and Linux. This API takes a command and a permission profile. If the permission profile allows limited network access, the caller must supply a network proxy to enforce those limits:

This function starts the processin a sandbox and returns aChildhandle the harness can use to wait for it to finish. Each child process inherits its parent’s sandbox constraints, so those restrictions apply throughout the process treeinitiated by thecommand, even to descendants that outlive the original process.

## Configuring the sandbox

A named permission profile lets you reuse the same filesystem and network restrictions across projects. You can define your own profiles under[permissions]inconfig.toml. For example, the following defines a profile nameddevthatextends⁠(opens in a new window)the built-in:workspaceprofile:

```
12default_permissions = "dev"34[permissions.dev]56description = "Development with extra read-only protections."78910extends = ":workspace"1112[permissions.dev.filesystem]13"~/build-cache" = "write"1415[permissions.dev.filesystem.":workspace_roots"]16".devcontainer" = "read"17".vscode" = "read"18"**/*.env" = "deny"19"secrets" = "deny"
```

Thedevprofile adds write access to~/build-cacheand places additional restrictions on files in the workspace. Filesystem entries can grant read-only access (read), grant read and write access (write), or block access entirely (deny).

The:workspace_rootstable lets you define rules for paths relative to a project’s workspace roots. By default, the Codex CLI uses its working directory as its sole workspace root, while the ChatGPT desktop app uses the project’s source folders. Codex applies each rule to every root, so the.vscodeentry indevmakes the.vscodedirectory read-only under each root.

In addition to its own rules,devinherits the following protections from:workspace:

```
1[permissions.":workspace".filesystem.":workspace_roots"]2".agents" = "read"3".aws" = "read"4".codex" = "read"5".git" = "read"
```

### Layering configuration and enforcing limits

Individual users can configure defaults that apply across projects and override them for a particular trusted project. Enterprise administrators may also want to configure defaults for their users and constrain which settings those users can change. Codex supports both through layered configuration and managed requirements.

As described inConfiguration precedence,⁠(opens in a new window)Codex merges settings from multipleconfig.tomlfiles. Tables are merged recursively, with the higher-precedence source winning when values conflict. Arrays are replaced as a whole.

This is why permission profiles use tables for filesystem paths and network domains. A team can add or override individual entries in its own configuration and automatically inherit changes to all other entries in the organization’s base configuration:

```
1[permissions.dev.filesystem.":workspace_roots"]2".idea" = "read"34[permissions.dev.network.domains]5"example.com" = "allow"
```

Administrators can also supplymanaged requirements⁠(opens in a new window)throughrequirements.tomlto constrain users’ configuration choices. These requirements can come from multiple sources, including system files and cloud-provided policy. A common use case is to specifyallowed_permission_profilesto constrain the set of permission profiles an enterprise user can select. For example, an administrator could specify these cloud requirements:

```
1default_permissions = ":read-only"23[allowed_permission_profiles]4":read-only" = true5":danger-full-access" = false
```

The cloud requirements would take precedence over the system requirements file at/etc/codex/requirements.toml, so an entry in that file cannot override the explicit":danger-full-access" = falseabove. Leaving:workspaceunspecified allows another requirements layer to supply that entry. Profiles whose entries arefalseor absent from the final merged table are unavailable.This separation lets organizations enforce limits while users tailor their configuration within those limits. The resulting permission profiles can be used by the harness or applied directly to a command, as we’ll see next.

### Example: sandboxing an MCP server

## Codex sandbox implementation

The sandbox implementation turns a permission profile into restrictions enforced by the operating system. The network proxy’s core request-handling and policy logic is shared across all three major operating systems, while proxy setup and integration with the sandbox are OS-specific. We’ll examine the shared proxy first, followed by the implementations for macOS, Linux, and Windows.

### Network proxy

To enforce a permission profile’s network restrictions, the harness starts a network proxy and configures the sandbox to allow connections to it while blocking direct connections to external hosts. The proxy checks each request against the profile’s domain rules to determine whether to forward it.

In the Codex repo, the network proxy is implemented in thecodex-network-proxy⁠(opens in a new window)crate, which the harness uses as a library, though it can also be built as astandalone CLI⁠(opens in a new window). When enabled,codex-network-proxystarts both an HTTP proxy and a SOCKS5 proxy by default. These proxy addresses are communicated to the process spawned by the sandbox via environment variables. In addition to injecting standard environment variables such asHTTP_PROXY,HTTPS_PROXY, andALL_PROXY, a number of well-knownapplication-specific environment variables⁠(opens in a new window)(such asPIP_PROXY) are injected, as well. Admittedly, not all programs honor these environment variables. If a program attempts a direct connection to an external host, the operating system’s sandbox restrictions block it, as described in the platform-specific sections below.

The network proxy is responsible for implementing the network restrictions defined in a permission profile. For example, thedevprofile shown earlier allows requests to*.openai.comand explicitly denies requests toevil.example. When a request targets a domain that does not match an allow or deny rule, the proxy can suspend the request while it delegates to the harness for approval. Like the shell command example, Codex may prompt the user directly, or it might route the request toauto-review⁠(opens in a new window). Upon receiving a decision, the proxy either allows the request to proceed or rejects it with an error response.

The order matters here because even a DNS lookup can leak information encoded in a hostname. The proxy therefore resolves the requested hostname only after determining that it is allowed or approved. Note that broad wildcard rules or access to DNS services can still permit DNS-based exfiltration.

### Linux

To create the sandbox on Linux, Codex uses a combination ofbubblewrap⁠(opens in a new window)(bwrap), a command-line tool for constructing isolated environments, andseccomp-bpf⁠(opens in a new window), a Linuxkernel mechanism for filtering system calls. An internal helper namedcodex-linux-sandboxcoordinates the setup. Likesandbox-execon macOS, it takes a sandbox configuration followed by a command to run:

```
1codex-linux-sandbox SANDBOX_ARGS... -- PROG ARGS...
```

When filesystem isolation or proxy routing is required,codex-linux-sandboxinvokesbwrapto create the initial sandbox environment.bwrapthen launchescodex-linux-sandbox --apply-seccomp-then-execinside it. This second invocation uses seccomp-bpf to apply additional restrictions before running the user’s command.

To construct that initial sandbox environment, Codex uses bubblewrap to create a filesystem view in a separate mount namespace that reflects the permission profile’s filesystem rules. Because this is fundamental to the sandbox implementation, Codex vendors its own copy ofbwrapin case the user has not installed their own, but itprefers a compatible installation of⁠(opens in a new window)bwrap⁠(opens in a new window)found onPATH, when available. Empirically,some Linux distributions disable access to user namespaces by default⁠(opens in a new window), but grant an exception for the systembwrap.

Also likesandbox-exec,bwraptakes a sandbox configuration followed by a command to run within the sandbox. Instead of using a custom config language like SBPL,bwrapuses individual flags for configuration. Codex uses the following options to create the filesystem view:

#### Connecting to the network proxy

When the sandbox configuration merits the use of the network proxy, the Codex harness creates one instance of the proxy that can be reused across multiple invocations ofcodex-linux-sandboxwithin the same Codex thread. Each sandbox needs a way to reach that shared proxy from its isolated network namespace. Codex provides a loopback TCP listener inside that namespace and arranges for a process outside the sandbox to accept its connections and relay them to the proxy.

The following diagrams illustrate this setup for one proxy endpoint, with one connection through it shown in the final diagram. Before launching bubblewrap,codex-linux-sandboxcreates a Unix socket pair to serve as a control channel and forks itself. The child runsrun_host_bridge()and waits to receive the listener’s file descriptor over that channel:

Inside the sandbox’s network namespace, the second invocation ofcodex-linux-sandboxcreates a loopback TCP listener and passes its file descriptor via the socket. The listener remains associated with the sandbox’s network namespace, allowing the child process that remained outside the sandbox to accept connections from sandboxed programs while opening its upstream connections in the host’s network namespace. After the handoff, both processes close their control-channel descriptors, and the process inside the sandbox closes its copy of the listener.

Once the TCP listener is ready, the process inside the sandboxsets the appropriate value forHTTP_PROXY⁠(opens in a new window)and related environment variables to point to that listener. It then applies seccomp before forking and executing the user’s command:

For each accepted connection, it opens a connection to the configured proxy and relays data in both directions.This additional machinery gives the command its own network namespace, including a separate loopback interface. On macOS, Seatbelt allows the command to connect directly to specified ports on the host’s loopback interface. On Linux, the command instead connects to a listener inside its isolated namespace, and a process outside the sandbox relays those connections to the configured proxy. The descriptor handoff makes this connection possible without exposing the host’s network namespace to the command.

- Need for elevated/admin access to set up the sandbox

#### Drive-root access

MXC’s filesystem policy denies access by default. Codex therefore adds read-only grants for the local drive roots to provide the broad reads allowed by this profile. These grants apply recursively, subject to the user’s existing OS permissions.

One wrinkle:writabledrive-root grants do not apply recursively, so Codex expands them to include the drive’s existing immediate children.

#### Conflicting grants

More-specific paths override ancestor grants, soC:\work\democan be writable beneath a read-onlyC:\, whileC:\work\demo\.gitremains read-only.

When different path spellings or symlink/junction aliases refer to the same path, MXC applies the stricter permission: deny takes precedence over read-only, which takes precedence over read-write.

#### Deny globs

MXC takes concrete deny paths only, so Codex expands deny globs to matching files and directories before launch. New paths that match the glob are not automatically added while the command is running.

#### Network access

Domain rules such as*.openai.comare enforced by the shared Codex network proxy described earlier. Codex runs that proxy outside the sandbox and passes its addresses to the command through the same standard*_PROXYenvironment variables as mentioned previously. MXC blocks direct external connections while allowing host-loopback connections, including access to the proxy. Other local services remain reachable.

Across macOS, Linux, and Windows, the harness uses the same sandbox API to launch commands under a permission profile. The platform-specific implementations handle the setup needed to apply those restrictions.

## Building on the Codex sandbox

Writing and executing code gives agents a flexible way to solve problems beyond software development. The Codex sandbox lets them use that capability in the user’s existing environment with explicit limits on filesystem and network access. It is a reusable primitive within the harness, and thecodex sandboxcommand makes it available to tools you build yourself.

As agents take on more tasks, we want to make sandboxing practical for more tools and environments. That means making permissions easier to configure and taking advantage of better operating system protections as they become available. Our goal is to expand what agents can do while keeping people in control of what they can access.
