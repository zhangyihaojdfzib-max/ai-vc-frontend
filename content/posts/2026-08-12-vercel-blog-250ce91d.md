经过多年的增长，代码库每月收到 100 多个新 issue，当 Anthropic 的 Opus 4.6 模型发布时，PR 数量达到了一个拐点。到 6 月底，积压的问题已累积到超过 1000 个未关闭的 issue 和近 800 个拉取请求。

这种积压不是纪律问题。无论维护者多么优秀，仅靠更努力地工作都无法弥合这一差距，而且由于生成代码的成本很低，积压只会继续增长。

我们没有试图扩大自身规模，而是建立了一个软件工厂。四周之内，它编写了我们合并的 PR 的 25% 到 35%，并关闭了 70% 到 80% 的 issue。

## 决定建造什么类型的工厂

在我们构建任何东西之前，我们必须回答三个问题：

- 为什么我们现有的使用 Agent 的方法不够好
- 什么样的自动化水平适合像 AI SDK 这样的项目
- 如何将自动化与人力投入与风险相匹配

### 为什么不添加更多 Agent？

最优秀的维护者已经在积极使用 Agent。Mitchell Hashimoto 运营 Ghostty 的目标是始终有一个 Agent 在工作，并将每次 Agent 的失败都编码到 AGENTS.md 中，以确保失败不会重演。Simon Willison 并行运行四个编码 Agent，而像 Vercel Agent 和 CodeRabbit 这样的审查机器人则部署在数百万个代码库上。其他维护者如 Daniel Stenberg 则选择阻止 AI 生成的提交进入 curl。

所有这些都有帮助，但都没有解决核心约束：这些解决方案中的每一个仍然将每次更改都路由到一个人的注意力上。我们相信，人的责任仍然是 Agent 工程中信任的核心，因此我们知道我们的工厂需要将审查者的效率作为第一原则来解决。

### 什么样的自动化适合 AI SDK？

软件工厂处在一个光谱上。一端是完全自动化，Agent 编写、发布和部署代码，而人类从不阅读代码。中间是像 Codex 和 Claude Code 这样的工具，由人引导一个或一组 Agent。另一端是你几乎不想自动化的软件，因为风险太高，比如心脏起搏器或自动驾驶汽车中的固件。

AI SDK 需要更靠近谨慎的一端。它是基础性的 AI 基础设施，有数百万个应用程序构建在其之上，因此质量和安全性是没得商量的，并且需要由人来控制发布的内容。我们需要我们的工厂在人的周围大力自动化生命周期，但不能将人移除。

### 我们如何将自动化和投入与风险对齐？

对于给定的更改，所需人工审查的深度随风险而变化。

带有详细功能规格的集中式路线图可以预先定义风险，并直接塑造进入软件工厂的工作。但像 AI SDK 这样的开源项目也会收到来自社区的 issue 和拉取请求，并且无法保证它们与项目的目标一致，或者更改是安全的。更高的风险意味着人的判断力成为系统中更为关键的部分。

为了优化我们的工厂以利用这种判断力，我们知道 Agent 必须超越基于请求生成代码；它们需要在整个项目的背景下评估完整的工作单元。

我们的目标是让工厂对每项更改的契合度和风险都生成全面的评估，包括完整的、有记录的证据链，使审查者能够轻松地投入适当的精力：

- 文档修复只需快速浏览验证
- 定义明确的提供商更改需要集中验证
- 新的公共 API 需要深入审查

## 我们构建了什么

ai-sdk-factory 是一个软件工厂，可以自主处理 AI SDK 的传入 issue 和拉取请求。工厂中的 Agent 执行特定的、可审查的任务，例如复现错误、实现功能以及为旧版 SDK 创建 backport。在整个过程中，人始终处于控制地位，包括合并每一项更改。

我们不是一蹴而就地推出工厂的。我们是从流程的起点开始逐步构建的，首先将 issue 分类为错误、功能或文档更新。这第一步不仅让我们更清晰地了解了积压工作的形态，还为后来构建的其他专门 Agent 传递了有用的上下文。

我们为每种新功能类型尝试了多种构建方式，并在此过程中形成了一套指导原则，这些原则塑造了投入生产的工厂架构。

### 每个任务构建一个 Agent

一旦我们的分类 Agent 达到了较高的准确率，我们就专注于自动化错误复现、修复以及对这些修复的审查。我们探索了构建一个配备各种技能的单一 Agent 来处理每个步骤，但很快意识到，随着时间的推移，这会带来更高的维护和故障排除负担。

相反，我们为每个特定任务构建了一个单独的 Agent，使每个新能力都更容易推理、隔离测试和调试。每个 Agent 都针对特定工作，拥有自己的提示词、上下文和评估。

### 从一开始就确保一切安全

我们在构建第二个 Agent 时实施了安全措施，因为错误复现是工厂根据其无法控制的内容执行代码的第一步。

在公共代码库上运行的工厂必须假设输入是攻击者控制的：每个 issue、拉取请求、评论以及其中的链接都是不可信的。由于成功的开源项目是高价值目标，威胁范围从恶意代码更改和供应链攻击到资源耗尽、API 密钥泄露和提示词泄露。

沙箱是我们防御体系的基础。在ai-sdk-factory中运行的每个Agent（智能体）都位于一个隔离的Vercel沙箱内，其中包含其代码、运行时，以及该Agent特定任务所需的唯一密钥。有了这些防护措施，不受信任的内容可以影响Agent的提议，但任何单个任务可能造成的损害都被限制在沙箱内。

我们还在沙箱周围构建了一个屏蔽层，用于控制Agent可以通过网络访问的内容，阻断攻击者从隔离环境中窃取密钥的路径。

最后一道防线是人工审查：未经AI SDK团队人员批准，任何内容都不会合并。

### 先在本地构建价值，再迁移到云端

我们为工厂构建的最初几个Agent是通过本地CLI运行的。这使我们的团队能够快速迭代，因为我们发现了不准确之处、感受到了摩擦，并原型化了不同的想法。

## 改进工厂成为工作本身

经营这个工厂最有趣的部分，是当它出错时会发生什么。每一次运行最终都会以四种方式之一结束：成功、有缺陷、受阻或人工处理。只有成功的结果才会交付，因此其余的结果都是信号，会以反馈的形式重新进入系统。

- 有缺陷的运行意味着某个Agent产生了错误的结果，解决办法是改进提示词、优化上下文，或新增一个评估用例，以便下次同样的错误能被自动捕获
- 受阻的运行意味着环境中缺少了某些东西，比如凭证、服务或依赖项，解决办法是进行配置补充
- 人工处理的运行标记了我们有意划出的一条边界，并迫使我们思考：工厂的改进是否足以证明移除这条边界是合理的
