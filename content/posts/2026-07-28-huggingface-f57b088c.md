# OlmoEarth 平台：行星尺度的地理空间推理

🌍 了解更多关于 OlmoEarth 平台的信息：https://allenai.org/olmoearth

![在 OlmoEarth 平台上生成的北美野火风险图，以卫星底图上的蓝到红热力图形式呈现](/images/posts/e27b34f6177b.png)

OlmoEarth 模型是我们系列的地球观测基础模型，基于约 10 TB 的多模态卫星数据进行预训练。政府、非政府组织及其他使命驱动型组织已在将 OlmoEarth 应用于森林砍伐监测、粮食安全和野火风险等领域。

在 Ai2，我们深知如何训练和发布强大的开源模型，对于拥有强大工程团队的组织而言，开源模型足以满足其需求。但环境领域的大多数组织——那些最适合应用这些模型的机构——并不具备管理完整生命周期所需的基础设施或工程团队：标注数据、微调模型以及运行大规模推理。我们运营 Skylight 和 EarthRanger 等平台已有十多年经验，这些软件全球用户每天依赖，因此必须每天稳定运行。这段经历让我们明白实现影响力需要什么：以合理的成本在正确的时间和地点运行模型，监控性能，将原始输出转化为可执行的洞察，并验证这些输出能够推动合作伙伴期望的结果。

正因如此，我们构建了 OlmoEarth 平台：将地理空间模型从微调和评估推向大规模推理的基础设施。

这种规模的推理本身就带来了一系列挑战。卫星图像需要跨多个提供商查找和获取，跨投影和分辨率进行对齐，并高效处理。随后，结果必须拼接成地理上一致的图像，同时基础设施要从分布式计算的常规故障中恢复。

如今，该平台可以在大约一天内完成跨大陆规模的推理，处理数十 TB 的图像数据，每平方公里成本不到一美分。开发这一平台意味着要面对一系列工程挑战，其他从事大规模地理空间系统工作的团队很可能也会遇到。本文将介绍这些挑战以及我们找到的解决方案。

### 为什么卫星推理具有挑战性

大多数机器学习模型接收几 MB 的数据并在不到一秒内产生结果——想想 LLM 处理一段文本或计算机视觉模型分析智能手机拍摄的照片。地球观测推理的运行规模截然不同——单个微调基础模型以实现最佳性能的任务可能移动 TB 级数据并运行数小时。输入可能跨越多个光谱波段、传感器类型和跨大地理区域的时间步长。这些数据可能来自多个提供商，每个使用不同的投影和分辨率，并且可能包含缺失或被云层遮挡的观测数据。输出本身是一张地图，因此每个预测必须与周围区域保持精确对齐到相同的投影和坐标网格。

即使获取数据本身也可能是一个重大挑战。预测任务通常花费更多时间下载和准备图像，而非运行模型本身，这使得高效的数据管道至关重要。这些管道必须处理高吞吐量的 I/O，同时提供重新投影和重采样图像所需的计算能力。

### 为合适的任务选择合适的硬件

由于数据获取和准备通常主导推理任务的运行时间，将这项工作分配给 GPU 会让系统最昂贵的硬件执行更适合 CPU 的任务。因此，我们将每个任务分为三个阶段，每个阶段匹配不同的硬件配置：

- 数据获取和预处理（CPU，高 I/O）：获取、重新投影、对齐和归一化图像，然后以优化格式写入，以便在推理期间快速加载。
- 推理（GPU）：运行模型的前向传播，并将最小化处理的输出直接写入存储。
- 后处理（CPU）：将每个窗口的输出拼接在一起，应用掩码或重新缩放，并以用户友好的格式（如 Zarr、GeoTIFF 或 GeoJSON）导出。

OlmoEarth 平台将这些阶段分布到多台机器上，同时保持 GPU 充分利用。多进程数据加载器持续为每个 GPU 提供数据，而完成的输出则直接流式传输到对象存储。

### 一个请求，数百个工作节点，数千个进程

OlmoEarth Run 是该平台用于大规模推理任务的执行层，它将每个任务覆盖的地理区域划分为适合单个计算实例（工作节点）大小的分区，然后将这些分区进一步细分为 OlmoEarth 模型处理的较小窗口。由于每个窗口可以在单独的前向传播中独立处理，地图某一部分的工作无需等待另一部分完成。

在实践中，一个州大小的区域可能变成大约一百个分区，而一个大陆规模的运行可能变成数千个分区。相邻分区略有重叠，我们在组装输出时处理这种重叠，以确保最终栅格中不出现接缝。

由于分区是独立的，同一阶段可以同时在数千个计算实例上运行。我们最近使用这种方法生成了覆盖整个北美的野火风险图。在峰值时，该运行并行使用了约 19,600 个 CPU 和 994 个 GPU，网络吞吐量超过 168 GB/s。这种并行度将估计的 4,737 小时串行计算减少到约 30.5 小时的挂钟时间——加速比达 155 倍。

然而，扇出并非无限制。更多的工作节点会触及云配额限制，因此并行度是每次运行的一个可调参数，也是我们可以针对单个任务调整的多个参数之一。输出分辨率在数据量和计算量与细节之间权衡；模型大小在 GPU 时间与准确性之间权衡；缓存原始图像在存储与速度之间权衡，适用于对同一区域的重复运行。正确的设置取决于手头的任务——以及预算。

### 查找和获取正确的像素

给定一个地理区域和时间范围，平台首先必须确定哪些卫星场景应输入模型。这意味着要识别在不同提供商（拥有不同的目录、格式和发布延迟）中捕获了什么、在哪里捕获以及何时捕获。选择标准也取决于数据源：对于光学图像（如 Sentinel-2），我们通常希望获取可用场景中云量最少的；而对于合成孔径雷达，可用的极化通道可能更为重要。

我们尽可能依赖公共 STAC 目录和开放标准。但一个大型推理任务可能同时生成数千个元数据查询——远超过 ESA 或 Microsoft Planetary Computer 的 STAC API 等外部服务设计用于并发处理的数量。

为了避免让这些服务不堪重负，OlmoEarth 平台维护了自己的元数据索引，并在新影像发布时进行更新。对于通过 AWS 开放数据托管的数据库，我们会为每个新场景接收一条 SNS 通知。当数据提供商不提供变更流时，我们会每隔几分钟轮询其上游索引。因此，我们对外部服务的请求会遵循新数据发布的稳定节奏，而不是由大型推理任务引发的突发性激增。

![OlmoEarth 数据库架构：一个覆盖多个卫星提供商（AWS 开放数据、Google Cloud、USGS、哥白尼计划、NASA/ASF、微软行星计算机）的元数据索引，为摄取队列、工作 Pod 以及一个为搜索和瓦片 API 提供服务的 Elasticsearch 索引提供数据](/images/posts/14138e8e76f7.png)

每个索引条目都存储了场景元数据，以及指向底层像素数据所有可用位置的指针。在运行时，平台会选择最佳数据源，并对 COG 或 Zarr 等云端优化格式执行窗口化读取，仅检索给定分区所需的字节，而无需下载整个场景。

该索引还支持我们的标注工具。由于它维护了指向以云端优化格式存储的 Sentinel-1、Sentinel-2、Landsat 和 NISAR 影像的指针，我们可以通过相同的窗口化读取系统，为任何已索引的场景提供瓦片服务，而无需构建单独的摄取管道。

使这一工作流程最为顺畅的数据提供商具备三个共同特征，我们建议将其作为发布地球观测数据的最佳实践：新影像可用时提供基于队列的通知；在主流云平台上进行存储，无特殊速率限制或可用性瓶颈；以及支持范围读取的云端优化格式。

### 大规模处理故障

OlmoEarth 平台设计为能够自动从故障中恢复。对于某个阶段和地理分区内的每个任务，它会动态配置一台运行我们 Runner Docker 容器的虚拟机。Runner 检索任务参数、执行工作、返回结果，然后关闭。由于每个任务都是可重入且幂等的，间歇性故障可以通过重新运行来安全处理。

在这种规模下，故障是预料之中的：提供商可能响应缓慢或短暂不可用；元数据可能指示影像存在，但所需的波段或窗口却缺失；云层可能导致可用观测数据过少；或者任务可能直接崩溃。平台的应对措施包括：任务跟踪、自动重试、在可用时回退到其他提供商，以及明确区分可重试错误和致命错误。一个独立的监控进程会检测到已停滞或停止的 Runner，并重新启动其任务。

### 未来方向

我们的路线图由合作伙伴发现的差距及其最迫切需要的功能所塑造。我们正在研究的领域包括：

- **自动化模型运行**。提前安排推理任务，或者在影像索引记录到感兴趣区域有新场景时触发推理。
- **变化检测与告警**。当用户监测的景观发生变化时通知用户，使森林砍伐或洪水等事件以告警形式呈现，而不是需要有人手动查找和检查的栅格数据。
- **Agent（智能体）工具与界面**。Agent（智能体）可以降低使用地理空间模型的门槛，涵盖从数据整理和特征工程到寻找改进微调模型的方法。我们希望任何技术水平的用户都能完成以前需要经验丰富的机器学习研究员才能做的工作。
- **更快的模型**。与研究团队合作，开发更高效的架构，减少每个窗口的 GPU 时间。
- **更多模态**。将新的卫星传感器和数据源纳入 OlmoEarth 模型及其所依赖的影像索引。我们目前正专注于整合天气数据（ERA-5）以及能提供更多环境因素细节的卫星。
- **嵌入/向量**。开发专用的嵌入模型，并在全球范围内预计算嵌入/向量。对于许多任务，针对这些嵌入/向量进行推理可以替代对原始影像的完整前向传播，从而使工作负载显著加快且成本更低。在最具挑战性的任务上，微调和直接推理对于实现最佳性能仍然重要，但嵌入/向量可以开启更广泛的、高效的应用程序。
- **随处运行**。OlmoEarth Run 仅需要能够运行 Docker 镜像的虚拟机以及对对象存储的访问权限。我们目前将其部署在 Google Cloud 上，但该架构设计为支持多云环境，并可在合作伙伴自己的账户和计算环境中进行部署。

这仅仅是个开始。地理空间基础模型，尤其是将其投入实际应用，仍然是一项新兴技术。许多最有条件使用这些模型的组织——那些致力于保护、粮食安全、灾难响应和气候领域的组织——此前从未接触过这样的基础设施。这些团队需要了解地球的认知，与其预算和技术资源所能支持的行动之间，仍然存在巨大差距。

我们正在构建 OlmoEarth 来帮助弥合这一差距。
