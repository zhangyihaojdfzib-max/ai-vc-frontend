On October 2 at Supabase Select we shipped Declarative Schemas 2.0. The Supabase CLI now generates migrations withpg-delta, a Postgres diff tool we wrote and open sourced, in place ofmigra, the technology behind our original implementation. Generated migrations now include RLS policy changes, grants, view settings, partitions, domains, and objects that extensions manage.

Declarative schemasfirst launched in April 2025. You keep your schema in SQL files undersupabase/schemas/, edit them, and the CLI writes the migration. In 2.0 that workflow is the same: edit a file, generate the migration, review it, and apply it. New CLI projects get 2.0 by default. Existing projects opt in with one config block.

In this post we cover why we builtpg-delta, how to turn it on, a working example, and what it does not do yet.

## Why we builtpg-delta#

migrais an open source Python tool that diffs two Postgres databases and emits the SQL between them. It has poweredsupabase db diffsince the first CLI prototype in 2021.

migradidn't understand domains, publications, or comments. Changes to them never appeared in the diff. You read every generated migration line by line to find what was missing. The limitations list in our docs kept growing and the answer for each entry was the same, write a versioned migration by hand.

Coverage was only half the problem. Supabase manages part of every project's schema. Theauthschema belongs to the Auth service and should never appear in your diff. A trigger onauth.usersthat calls a function inpublicto create a profile row is yours and has to appear. The same split runs through roles, grants, and extension-owned objects.migracould only filter at the schema level so it had no way to keepauthout while keeping that trigger in. We needed an engine that decides per object what belongs to you and what belongs to Supabase.

We felt these gaps ourselves. We usemigraon our own middleware database, and our repository carries dozens of migrations with hand-written patches for the grants and privileges it didn't track. Extending it further meant fighting its design. So we wrote our own engine from scratch and open sourced it.

## Howpg-deltabuilds a migration#

The CLI starts two throwaway Postgres databases. It loads your schema files into one and replays your migration history into the other.pg-deltathen compares the two by reading the system catalog, and orders the output using a dependency graph built from that catalog. You no longer hand-order files inschema_paths.

Everythingmigra's docs listed as unsupported is now in the diff. It also covers partitions, publications, subscriptions, and foreign tables.

Objects that an extension owns are changed through the extension's own API.pg-deltanever emitscreate tableordrop tableforpg_partmanpartitions orpgmqqueue tables. It emits calls likeselect pgmq.drop_queue('q');, and the CLI flags them as destructive.

Unsupported objects produce a warning. Pass--strict-coverageto turn those warnings into errors so CI fails.

The output is a plain SQL file insupabase/migrations/. Hand-written migrations keep working. Oncepg-deltais on,db diffanddb pulluse it too.

Pay extra attention to anything the CLI flags as destructive.pg-deltaprioritizes coverage and correctness over producing the least destructive migration. A renamed column, for example, comes out as a drop followed by an add. Running that migration unchanged would wipe the column's data. The CLI flags the drop but it cannot know you meant a rename. Less destructive migrations are on the roadmap. Until then, rewrite flagged statements by hand before you apply.

## We builtpg-deltatwice#

Thepg-deltain this post is the second one we built. The first engine powered branch merge diffs in the dashboard from February 2026 and the CLI from March, went out as apublic alphain April, and stayed in production until August. It worked. A few months of production traffic showed us where its design would stop scaling. Its knowledge of Postgres lived in several places at once. A parser inferred types from SQL text while a separate layer read the catalog. Whenever the two disagreed, the diff was wrong. Every new thing we taught the engine was another chance for them to disagree.

In June we started over with one rule: Postgres is the only thing that understands Postgres. The new engine never parses SQL. ## What stays out of scope#

pg-deltagenerates schema changes rather than data changes. It creates tables, policies, and functions. It never writes aninsert,update, ordeletefor the rows in your tables.

There is one exception. Some extensions store their configuration as rows. Apg_cronjob, for example, is a row incron.job.pg-deltatreats those rows as part of your schema. It changes them through the extension's own functions. A new job comes out ascron.schedule_in_databaseand a removed job ascron.unschedule. A changed job comes out ascron.unschedulefollowed bycron.schedule_in_database.pgmqworks the same way. A queue is a pair of tables thatpgmq.createbuilds for you, plus a row inpgmq.meta.pg-deltanever emitscreate tableordrop tablefor those tables. It emitspgmq.createandpgmq.drop_queueinstead and the CLI flags the drop as destructive.

Storage buckets are not included today. A bucket is a row instorage.buckets.pg-deltadoes not diff its rows. A bucket you create in the dashboard will not show up in your schema files. Until that changes, create buckets in a seed file or a hand-written migration instead. The RLS policies onstorage.objectsare a different story. They are schema and are diffed.

Declarative Schemas 2.0 is a diff engine and a set of CLI commands. It does not include:

- Zero-downtime rollout orchestration.The output is a plain SQL migration. Running it safely against production is still your job.
- An ORM plugin or a TypeScript schema DSL.The schema files are SQL and nothing else.
- Postgres 13 or older.The engine supports Postgres 14 through 18.
