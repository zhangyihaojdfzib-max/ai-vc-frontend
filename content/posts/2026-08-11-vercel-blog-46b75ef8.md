Vercel 上的每次构建都始于构建预热池（build warm pool），这是一组待命容器，让构建无需等待新计算资源即可启动。该池运行在一种状态之上，这种状态跟踪哪些容器已就绪、每个容器用于认证的令牌，以及将每个运行中的构建映射回为其计费的部署。当我们最初构建这个池时，我们将所有这些状态存储在 Redis 中，当时它速度很快，也合情合理。

然而，多年之后，这些状态变成了一种负担。令牌和容器状态如果丢失可以重建，但计费映射无法重建，而所有这些数据都存放在我们作为临时缓存运行的存储中。这些状态需要保存在持久化存储中，这就是我们决定将其迁移到 DynamoDB 的原因。

问题在于，预热池从不停止运行。容器全天候地启动、轮询、接收任务和过期，这意味着我们无法暂停整个系统、复制数据然后重新启动。迁移必须在生产流量下实时进行，分阶段推进，每个阶段都由一个功能开关控制，并在需要时准备好回滚方案。

## 临时存储中的持久化状态

Redis 起初是这些数据的理想归宿。它速度快、熟悉且高效，符合预热池最初访问模式的需求。但随着时间的推移，这些状态变得比存储它们的数据库更重要。如果 Redis 不可用或丢失数据，预热池将无法可靠地认证容器、跟踪哪些容器已就绪，或解析正在进行的任务。

丢失一个令牌，池大约十分钟内就能重建它。但丢失一个映射，该构建就永远不会被计费，因为没有其他记录能表明它属于哪个部署。

我们希望将其放入持久化存储中，最终选择了 DynamoDB。按需扩展适合突发性的部署流量，TTL 是原生功能，而且在高并发下无需管理连接。但它无法保证 Redis 那样的低延迟。

## Redis 让什么变得廉价

在 Redis 内部，预热池的状态结构如下：

- 令牌存储在一个集合（set）中以便检查成员资格，同时存储在一个有序集合（sorted set）中以便过期处理
- 每个生命周期状态（待处理、轮询、构建中）都有自己的有序集合，这意味着状态变更就是从集合 A 中移除并添加到集合 B 中
- 一个字符串将每个工作容器与其部署关联起来

所有这些操作都很廉价，每次大约一毫秒，代码也逐渐依赖这种速度。仅运行一次供应循环（supply loop，即依次为每个预热池补充容器的循环），就需要数百次计数调用，仅仅是为了统计待处理和轮询中的容器数量。

预热池就是这样逐步成长起来的，一次一次简单的写入，直到我们需要保留的数据被存放在为速度而设计的结构中。理清这种布局正是迁移的起点。

## 从访问模式设计 Schema

大多数迁移方案将数据库视为被替换的对象。你映射访问模式、复制数据，然后验证两个存储是否一致。我们最初也是这么规划的，因此在设计任何 schema 之前，我们列出了代码实际对该状态提出的所有请求：

- 容器轮询任务时验证令牌
- 新容器启动时添加令牌
- 使超过截止时间的令牌过期
- 统计令牌数量以确定池的规模
- 在生命周期状态之间移动容器
- 按状态统计容器数量
- 通过容器的回调查找对应的部署
- 移除已过期的容器

几乎每个操作都已经知道它正在操作哪个容器，只有轮询操作是从令牌开始的。因此我们将容器置于模型的中心。容器 ID 成为排序键（sort key），令牌只是记录上的一个字段，以哈希形式存储，这样读取表时永远不会直接暴露可用的凭据。现在验证令牌只需查找其对应的容器并比较哈希值即可。

其中两种访问模式无法仅通过键查找来满足。状态计数需要跳过已经过期的容器，这需要一个时间感知索引。而部署查找服务于计费系统，因此需要一致性读取，该映射单独使用了一个小表。

```
1type ContainerRecord = {2  warmPoolId: string   3  containerId: string  4  token: string        5  status: 'pending' | 'polling' | 'building'6  expiresAt: number    7}
```

这是我们最终上线形态的简化草图。三个状态有序集合变成了一个字段。

读取容器状态、变更其状态、清除其令牌都变成了直接的键查找。状态计数变为对时间感知索引的单次读取，每个状态一次查询，已过期的容器已被自动过滤。

```
12queryCount({3  partition: `${warmPoolId}#${status}`,4  where: 'expiresAt > now',5})
```

每个状态一次查询，受过期时间约束。

Redis 让数据结构隐式地表达我们所需的一切，而 DynamoDB 则要求我们明确指定键、索引、条件写入和 TTL 行为。因此，我们没有沿用 Redis 的数据结构，而是以容器为核心建模，并添加了其访问模式所需的索引。

## 影子模式验证了每次写入

部署以功能开关分阶段推进：仅 Redis、双写、影子读取、DynamoDB 主读，最后是仅 DynamoDB。每个阶段都尽可能长时间地保留回滚选项。最后一步移除 Redis 写入，是唯一没有简单回滚方案的一步，但任何残留的令牌都会在十分钟内过期。

我们首先对现有 Redis 操作进行基线测试，记录其数量和延迟，以便仪表板有正常基准可供对比。新的 DynamoDB 方法在实际被调用前数天就已合并。接下来是双写阶段，Redis 仍作为数据源，DynamoDB 的失败仅记录日志而非致命错误。然后是影子读取，同时查询两个存储并比较结果。最后切换为主读，Redis 写入保留到新路径被充分验证为止。

这些比较告诉我们两个存储是否在存储值上达成一致，这是仅靠测试无法验证的。它们无法说明时序问题。我们检查了每次写入是否都落入了两个存储、过期是否随着容器状态变化持续推进以避免陈旧状态堆积、清除令牌是否不影响容器记录的其他部分，以及计数是否足够接近以正确引导池的运行。

在比较之上，我们构建了仪表板，在 Redis 仍在服务生产流量时监控匹配率、写入错误、每次查询延迟和过期计数。这样任何偏差都能在调查成本还很低时浮出水面，而不是以切换失败的形式出现。每个不匹配都被追查为真实 bug、双写竞态或预期差异，然后才继续推进。这些仪表板决定了每个阶段何时推进，每当数字在生产流量下保持稳定，下一步就感觉更安全了。

## 过程中的两次失败

三月份，某个区域的构建服务发生了宕机，调查指向了我们自己的比对机制——即对两个存储进行检查所带来的额外负载。这个场景在评审时其实已经被预见到，我们也因此对比对操作进行了限流，但限流力度不够。四天后，一份引用该事件报告的拉取请求添加了状态计数所需的索引。没有这个索引，每次计数都是O(n)的复杂度，而比对操作又在持续不断地进行计数。索引到位后，发布得以继续推进。

同月下旬，我们正在迁移离开的Redis基础设施真的宕机了。温池及其Token处理保持正常运行，因为它们都已经从DynamoDB读取数据作为事实来源。构建服务仍然感受到了宕机的影响，但那是通过流水线中尚未迁移的上游服务传导的。我们一直在试图规避的故障在迁移完成之前就发生了，而已经迁移过去的状态则安然无恙。

## 供应循环因读取变慢而停滞

四月份，供应循环开始出现停滞。当我们提前主读取时，影子数据看起来是健康的，仪表盘上的单次查询延迟也看似可接受。真正出问题的是一种两者都没有衡量的行为。

我们绘制了循环图来定位时间消耗在哪里。

```
设计中的循环
  检查 → 创建 → 检查 → 创建 → 检查 → 创建 → ...          每个容器前一次状态读取
更慢的读取所要求的
  检查 → 创建, 创建, 创建, ... → 检查          不再每次创建前都进行读取
```

根据调查原始草图重新绘制。上面一行中的每个“检查”都是一次到存储的往返请求。

在`getWarmPoolTokenCount`的P95延迟上，Redis测得1.29毫秒，DynamoDB测得5.13毫秒。当时我们简化为每次查询慢两到三倍，事实证明这被低估了。

几毫秒的额外延迟本身不算什么，因为只需支付一次。但循环在每次创建容器前都要支付这笔开销，每次运行数百次，最坏情况下将运行时间拉长到几分钟，导致温池无法跟上需求。这个循环是一个N+1查询问题，而Redis只是恰好足够快，掩盖了这个问题。

没有人写过“这个循环需要毫秒级读取”这样的注释。但这个假设就存在于设计之中，而在每检查一次仅需一毫秒的情况下，从来没有触发过让我们停下来审视的问题。

## 我们围绕新的延迟重新设计了循环

DynamoDB永远无法达到Redis的毫秒级性能，所以我们没有去追逐这个目标，而是从设计上消除了这个需求。

第一次尝试是批处理，即草图底部所描绘的形式。差距的大小取决于你观察的是哪个百分位数，在P90（差距最大的位置），差距约为17倍。因此批处理设计每17个容器检查一次状态，一次读取摊分到整个批次中，这个常数直接来自测量数据。但这个常数也正是我们放弃该方案的原因。它硬编码了一个会随负载漂移的延迟比率，这意味着又多了一个对存储速度的隐性依赖。而并发方案根本不需要常数。

最终上线的方案是让循环中的供应调用并发执行，这样每个温池不再需要等待前一个温池完成，每次调用都基于它最后看到的状态工作。重叠读取为我们带来了与批处理相同的效果——没有任何一次运行会因单次读取而串行化。最坏的情况是基于池的过期视图多创建几个容器，这一点在拉取请求中被列为可接受的成本。重新设计意味着我们可以在不牺牲用户真正关心的东西——即构建快速可靠地启动——的前提下，保留更持久的存储。修复与发布一样，以一步一测的方式落地。正如我们其中一位成员所说：“每次迭代的风险都在降低，因为我们修正了之前的误判。”

事实证明，这个循环在Redis下也曾停滞过，有时长达一分钟甚至更久，而我们是在诊断DynamoDB时才发现的。证据一直存在于我们的遥测数据中，但因为温池位于需求之前而非任何请求路径中，在迁移之前从未有外力迫使我们去看。而这次重新设计最终移除了一个比项目本身还要古老的缺陷。

## 迁移假设

迁移于四月份完成，温池路径中的Redis调用已全部移除。事实证明，复制数据是最容易的部分。真正的工作是找出建立在存储之上的各种假设，然后重新设计承载这些假设的循环。每个构建所依赖的状态现在存储在一个为保存它而构建的存储中，管理它的循环也不再因任何单次读取而串行化。

四月复盘会将教训总结为一句话：“即使是P90上1毫秒到15毫秒的查询时间退化，也可能击垮我们的温池管理逻辑。”这句话在二月份迁移启动时，没有人写下来。
