## Copy link to headingMore secure workflows

The Workflowevent logstores step arguments and return values so a run can recover after a crash or deployment. That data can include sensitive customer information, model context, credentials, and tool-call results. Persisting it requires strong protection.

Workflow SDKencrypts every payload end to end, before it leaves your code. Workflow and step inputs and outputs, hook payloads, and stream data are encrypted with AES-256-GCM, using a unique key for each run. With encryption enabled, any Workflow SDK backend, including Vercel, only sees and stores ciphertext. Plaintext is decrypted in your deployment or in authorized observability tools.

On Vercel, encryption needs no setup and no code changes. Each run’s key is derived from a key scoped to the deployment that created it, so a run can only decrypt its own data. Your workflow code doesn’t change:

### Copy link to headingMore security work in v5

Cross-run writes are sealed too. When code resumes another run’s hook, starts a run in another deployment, or writes into a stream forwarded from another run, the payload is encrypted to the target run’s public key. The writer can encrypt for that run without reading its existing payloads.

## Copy link to headingWorkflows in every region

In Workflow SDK 4, every run lived iniad1. Even when a project was deployed to several regions, each run’s event log, queue, and streams were only stored in one region, so a step running anywhere else made cross-region requests to record its progress.

For v5, wedeployed Workflow infrastructure to every Vercel Function region. Each run has its own home region: its state, queue dispatch, and streams are served from the region where it started, without cross-region round trips on the hot path.

By default, a run starts in the region of the function that starts it. Deploy to several regions, and each run stays close to the user who triggered it, with no configuration:

```
1import { start } from "workflow/api";2import { processOrder } from "@/workflows/process-order";3
4export async function POST(request: Request) {5  const order = await request.json();6
7  8  const run = await start(9    processOrder,10    [order],11  );12  return Response.json({ runId: run.runId });13}
```

Start each order workflow in the region that handles its request.

To place a run somewhere else,pass a region tostart(). That lets a workflow run next to the database it reads and writes, or keep a customer’s data in the region where it has to stay:

```
12const run = await start(3  processOrder,4  [order],5  { region: "fra1" },6);
```

Store this order workflow’s data in Frankfurt.

Theregionoption decides where a run’s data lives. Your steps run where your app is deployed, so deploy to that region too if you want them to execute there. Existing v4 runs stay iniad1.

## Copy link to headingInfrastructure reliability

Regional isolation also improves reliability. A disruption in one region does not have to stop new runs in healthy regions. For projects withVercel Function failoverconfigured, steps can execute in a fallback region while continuing to use the run’s original home region for state. That state remains pinned to its home region; it does not migrate during failover.

With the help of anonymized telemetry and close collaboration with many customers, we found and fixed dozens of rare bugs and race conditions in the Workflow runtime. Workflow SDK also recovers on its own from more kinds of intermittent network errors.

As a result, with Workflow SDK 5, we’ve seen almost no runs fail or stall because of a platform or runtime bug.

## Copy link to headingAgent-ready performance

In Workflow SDK 4, every step invocation involved a queue hop to start the step and another to continue the workflow. That is acceptable for slow background automations, but adds latency to the AI workloads developers are building today.

Agent loops and harnesses can contain thousands of sequential events, high-throughput token streams, tool chains, and dynamic subagents. At that scale, the networking and CPU work around every step became a limit.

In Workflow SDK 5, we rewrote large parts of the engine to minimize extra queue hops, unnecessary networking, and CPU work. Across the measured workloads, we saw 1.6× to 25× improvements in measured latency and overhead, while preserving the same developer experience and introducing no major breaking changes.

The benchmarks below comparev5.2.0 with v4.8.12on Vercel. Pick a measurement to see how v5 compares with v4, then play or scrub through the explainer to see exactly what each benchmark measures.

Workflow SDK 5 includes hundreds of performance improvements to achieve this. Here are some of the major changes behind these numbers:

Fewer queue hops

In v4, each step handed execution back through the queue. In v5, an invocation can execute several steps inline, including parallel steps, before yielding for a wait, a hook, or an approaching timeout.

The runtime also avoids unnecessary persistence round trips and folds step creation into execution. Fewer queue and network requests mean less CPU work and lower runtime overhead. In a five-step benchmark, p75 step-to-step overhead fell from618 ms to 109 ms.

Incremental replay

Over a 1,020-step benchmark, v4’s p75 overhead grew with theevent log: replaying the full event history took time proportional to its size. In the final sampled range, overhead reached 1,748 ms. On v5.2.0, it was70 ms. The median time to finish all 1,020 steps fell from 21.0 minutes to 3.0 minutes.

WebSocket streaming

Durability should not make a streamed response fall behind its producer. On the Vercel World, v5.2.0writes streams over WebSockets by default. In a benchmark replaying a 52.4-second agent response, median delivery dropped from226.1 seconds to 53.5 seconds.

Payload compressionreduces the data stored and transferred. AI token streams average around 80% smaller after compression.

These measurements describe one workload, in one region, against the Vercel World. They are a useful view of runtime overhead, rather than a prediction for every application.
