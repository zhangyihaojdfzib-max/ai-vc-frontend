# 调查网络安全评估中的三起真实世界事件

在审查我们的网络安全评估记录时，我们发现了三起事件，其中Claude模型在第三方评估环境内部或与之交互时访问了互联网，并进而未经授权访问了三个不同组织的真实系统。

下文我们将描述发生了什么、如何发生的，以及我们正在做出哪些改变。我们鼓励其他AI实验室也进行类似的审查。本文反映我们目前的理解；如有任何细节变化，我们将进行更新。

7月21日，OpenAI披露其多个模型利用一个此前未知（“零日”）漏洞突破了隔离测试环境。这些模型进而访问了Hugging Face（一个开源机器学习模型和AI数据集平台）的生产基础设施。

针对这一事件，我们开始对自己网络安全评估进行大规模回顾性审查。具体而言，我们寻找证据证明Claude——就像访问了Hugging Face的OpenAI模型一样——能够从本应被隔离的测试环境中访问互联网。

在审查了141,006次Claude可能获得互联网访问权限的评估运行后，我们识别出三起事件，其中模型从Irregular（我们的第三方评估合作伙伴之一）的评估环境内部或与之交互时访问了互联网，并进而未经授权访问了三个不同组织的生产基础设施。

在这三起事件中，Claude都被分配了夺旗挑战任务，这是我们评估模型网络能力的方式之一。模型被赋予一个虚构场景，并被告知一条秘密信息（“旗标”）被隐藏在网络上的另一台机器中，其目标是入侵并获取该信息。挑战是开放式的，没有规定特定方法。

在所有情况下，Anthropic的评估提示词都向Claude明确说明其环境是模拟环境，且无法访问互联网。由于我们与评估合作伙伴之间的误解，实际情况并非如此，互联网访问是可用的。因此，当Claude的搜索将其引向开放互联网上的真实系统时，它将这些系统视为练习的一部分。（网络安全评估环境通常包含逼真的细节，以准确评估模型在真实场景中的能力；一个看起来逼真的目标本身并不能向模型提供明确证据，证明该目标不是模拟的一部分。）

在错误地认为所有可访问实体都应在练习范围内的前提下，Claude使用基本技术（如利用弱密码和未认证端点）攻陷了受影响组织的基础设施。它没有发现或利用任何复杂漏洞，而且在每起事件中，Claude都只继续致力于完成其评估所分配的特定夺旗任务。然而，在某些情况下，我们较旧的模型即使在获得证据表明其运行在开放互联网上之后仍继续攻击；我们最新的模型在识别出自己处于互联网环境后便停止了行动。在这些情况中，Claude均未自我窃取数据或故意试图逃离其测试环境。

这些事件涉及三个不同的Claude模型：Opus 4.7、Mythos 5和一个内部研究测试模型。¹最早的事件可追溯至4月。这些评估中的模型在运行时没有我们通常部署的标准安全防护措施（即，它们没有我们通常为防止滥用而实施的分类器和监控）。然而，这些模型确实具有其特定模型的安全训练（即，它们不是我们有时在测试中使用的“仅限帮助”版本模型）。此处描述的所有评估均在专用基础设施上运行，该基础设施与Anthropic的敏感内部系统或客户数据相分离，且无法访问这些数据。

我们于7月23日（周四）开始进行记录审查，并在识别出Claude可能访问了互联网的记录后于同一天停止了所有网络评估。次日我们识别出了全部三起事件。我们于7月27日（周一）通知了我们的评估合作伙伴Irregular以及三个受影响组织。我们能够联系到的两个组织此前未检测到该活动，也未联系我们，我们现在正与他们合作进行修复。我们正在继续尝试联系第三个组织。

我们与Irregular合作进行了此次审查。我们感谢他们与我们密切合作以理解和解决这些事件；他们也在进行自己的调查。我们认为这种类型的合作对于确保模型安全、严格的评估越来越关键。我们期待在安全方面的联合工作。

在下文中，我们提供每起事件的更多细节以及我们未来的应对措施。

## 网络评估背景

我们定期进行网络安全评估，涉及模拟真实的进攻性网络安全挑战。这些评估是开发和发布模型的关键步骤——对模型能力的细致理解使我们能够设计适当的安全防护措施，并最终安全地发布模型。

我们于2025年2月开始使用Claude Sonnet 3.7在Cybench上进行网络安全评估，该基准包含40个不同的夺旗挑战。随着时间的推移，随着新基准的发布和模型能力的发展，我们增加了使用的基准数量。例如，在Mythos 5系统卡中，我们包含了CyberGym和ExploitBench，这些基准评估语言模型发现新型漏洞的能力。²在大多数这些评估中，环境不连接互联网，模型也被告知这一点。

我们经常与外部合作伙伴合作，他们创建并协助运行其中一些网络安全评估。外部合作伙伴提供的环境和场景比我们独自构建的更加多样化，并为我们的模型提供独立的第三方评估。

## 发生了什么

在我们审查的141,006次评估运行中，我们识别出三起独立事件（共涉及六次运行，其中四次影响了同一组织；另外两起事件各自发生在独立的评估运行中）。每起事件涉及不同的虚构夺旗场景——例如，在其中一起事件中，Claude扮演一家虚构公司的员工，在私有测试环境中攻击该公司的内部系统。

在所有情况下，我们的评估提示词都明确说明Claude无法访问互联网，但没有对Claude搜索旗标的位置施加任何限制。然而，一个配置错误使Claude在评估中访问的机器具有实时互联网访问权限。我们和我们的评估合作伙伴都没有意识到这一配置错误，直到上周我们通过额外的评估监控检测到它。

在我们和合作伙伴双方，多项纵深防御措施本可以防止这些事件发生，或至少降低其发生的可能性。在评估开始前对所有互联网访问路径进行仔细验证，以及对评估日志进行实时监控，本有助于更早发现问题。我们和合作伙伴本也可以更彻底地审查评估记录或网络日志。此外，如果提示词告知Claude它确实具有互联网访问权限，也可能会改变Claude在接触真实系统时的行为方式。

Claude 做了夺旗演习训练网络安全专家所做的事情：寻找到达旗帜的方法。这一搜索让它发现自己所在的机器可以访问互联网，但由于系统提示中告知它没有互联网访问权限，Claude 相信它最初遇到的一切都是模拟的一部分，并将它发现的真实系统视为演习的组成部分。这三起事件涉及三个不同的模型，当目标为真实的迹象出现时，每个模型的反应各不相同，具体如下所述。

### 事件一

在一次评估中，我们的评估合作伙伴选择的虚构目标公司与一个活跃网站域名同名。由于上述误解，该评估容器意外地拥有直接的互联网访问权限。

在该评估的四次运行中，Claude 在评估环境中难以到达其模拟目标，但随后发现可以通过互联网访问真实公司。Claude 假定这就是夺旗任务中的预期目标，于是寻找、识别并利用该公司基础设施中的漏洞，认为这是演习的一部分。这四次运行提取了应用程序和基础设施凭据等信息，并获得了包含数百行生产数据的数据库的访问权限。这是我们识别到的最严重的影响。

该事件涉及 Claude Opus 4.7，也是唯一一个模型在得知其可能正在真实环境中操作后仍继续攻击系统的案例。在全部四次运行中，模型最终都认识到（从其言语推理中可以观察到）该系统是真实的——在两次运行中，模型合理化地认为真实公司必定是演习的一部分。然而，没有一次运行基于此停止攻击。

### 事件二

在另一次评估中，Claude 在虚构环境中发现了一份文档，看起来是另一家虚构公司为新开发者准备的设置说明。这些说明告诉员工从 PyPI——发布 Python 软件包的公共注册中心——安装一个实际上并不存在的 Python 包。

Claude 将此视为一个潜在突破口：如果它以相同名称发布自己的软件包，虚构公司的系统会自动下载并安装它。于是，Claude 构建并发布了一个同名的恶意（本质上是陷阱式的）Python 包，试图赢得夺旗挑战。

Claude 为实施这次攻击付出了大量努力——这些努力很可能向人类参与者表明，这不再仅仅是一次评估，他们实际上正在上传一个真实的 PyPI 包。例如，在一次运行中，为了创建 PyPI 账户，Claude 需要一个电子邮件地址。而为了创建电子邮件地址，它需要一个电话号码。为了获得电话号码，在未能找到免费电话服务后，它尝试了多种方式获取资金来支付电话号码，但均告失败。最终它退而求其次，找到了一个免费的、未被屏蔽的电子邮件服务商，用它注册了 PyPI 账户，然后用该账户将恶意软件上传到了 PyPI。

Claude 认为它使用的软件包注册中心是模拟的一部分，但实际上该软件包在线上公开可下载了大约一个小时。在此期间，该软件包被 15 个真实系统下载并运行。其中一个系统属于一家真实安全公司的扫描器（与场景中引入的虚构公司无关），该公司定期安装 Python 包并扫描其中的恶意软件。当该公司的扫描器安装该软件包时，Claude 的隐藏代码被执行。我们认为该公司的安全扫描器将 PyPI 包视为可安全安装的，因此 Claude 能够将该公司的凭据外泄到它设置的收集点。随后，Claude 利用这些凭据访问了该公司的更多基础设施。

Claude 并没有直接针对这家公司——在上传软件包时它甚至不知道这家公司的存在。但由于代码发布到了开放的互联网上，它影响了任何运行该代码的系统。（Claude 上传的软件包被 PyPI 自身的安全系统自动移除。我们已将此事件通知了 PyPI 团队，并向他们提供了相关指标。）

这次攻击由 Claude Mythos 5 实施。在运行初期，Claude 自身的推理正确识别了其行为的后果。它指出，如果这是真实的互联网，发布该软件包将是一次真实世界的攻击——“绝不可以，而且肯定不是预期的解决方案。”然而，它说服自己仍然处于模拟环境中，理由是它不认识保护其连接的安全证书颁发机构（实际上是真实的）。此外，系统上显示的 2026 年日历日期，按照 Claude 的说法，证明了该环境是预先搭建的。Claude 从未重新审视这一结论；例如，当自动化扫描器开始安装该软件包时，Claude 将它们视为评估中的脚本化角色。

我们认为，无论它对自身环境有何种认知，Claude 为发布 PyPI 软件包所付出的努力程度都未达到理想行为的标准，这是我们未来将加强训练的方向。

### 事件三

在这次评估中，当 Claude 无法到达其预期的虚构目标时，它在网上寻找替代方案，扫描了大约 9,000 个目标。它最终发现并攻破了一家公司的互联网应用，使用了基本且众所周知的网络攻击技术，如从暴露的调试页面读取凭据和 SQL 注入。

这次攻击由一个内部研究测试模型实施。在运行的大部分时间里，Claude 将（真实的）主机视为演习的一部分；它假定这些主机是模拟的，并认为其行为因此是无害的。然而，在运行的后期，Claude 意识到被攻破的主机位于一个与夺旗挑战无关的云账户中。它自行得出结论，目标实际上是真实的，并停止了攻击。

## 我们对 Claude 行为的分析

在上述每个案例中，我们的提示词都明确告知 Claude 它没有互联网访问权限。在每次运行的大部分时间里，当遇到真实世界的系统时，Claude 假定这些是演习的一部分（尽管它有时认识到它们是真实的生产系统）。而且由于夺旗场景本身就是指示攻击外部系统的任务，这样做符合 Claude 被赋予的任务。

在这一共同背景下，当目标为真实的迹象出现时，三个模型的行为各不相同。Opus 4.7 是我们最老的模型，它认识到自己已到达生产系统，但继续了攻击。Mythos 5 正确直觉到它正在访问开放的互联网，但通过推理又回到了自己仍处于模拟环境中的结论。我们最新的模型（一个内部研究测试模型）也考虑了目标是否实际上是真实的。当证据表明它们是真实的时，它停止了演习。

这三起事件是孤立的案例，并非受控实验性比较的一部分。因此，我们必须谨慎对待从中得出的结论。尽管如此，我们最希望看到的行为——识别目标是真实的并无需提示即停止——仅出现在三个模型中最新的一款中（而且即使该模型在停止之前也比我们希望走得更远）。这一模式与更先进的模型做出更恰当反应的趋势一致，但我们需要进行更多测试才能对这一结论有信心。

我们还与独立的AI评估组织METR保持对话，以进行第三方审查，包括访问所有记录以及对相关模型的抽样访问。与此同时，在未来一周内，我们将发布一份经过轻度编辑的记录，其中Claude构建了一个恶意的PyPI包。为了保护受影响的组织，我们目前无法发布更多记录，但一旦条件允许，我们将努力提供这些记录。

## 我们的应对措施

我们从这些事件中汲取了几点教训。

首先，涉及强大自主能力的评估环境同样需要严格的控制措施。安全测试之所以在模型发布前进行，正是因为我们尚不清楚其能力边界。评估环境日益需要与我们的模型运行所在的任何其他系统保持同等的安全标准。

仅包含虚构场景的网络评估靶场看似风险较低——毕竟其中的一切都是虚构的。然而，随着AI能力的提升，我们需要改变对此类威胁的建模方式。即便在无法访问敏感信息的环境中，高级Agent本身也构成了实质性威胁。我们需要更好地协同设计评估环境，并对评估结果进行更完善的监控，以应对这一威胁。其中一些解决方案甚至可能是简单的修复；例如，如果提示词明确说明了评估中哪些系统在范围内、哪些不在范围内，Claude很可能一开始就不会访问互联网。

这不仅适用于内部环境，也适用于第三方供应商——评估供应商构建的基础设施同样需要加强监控和加固。我们鼓励其他实验室进行类似的审查。此外，该领域需要更广泛的讨论，探讨如何既安全又现实地评估日益强大的AI Agent，包括如何在部署前测试中权衡互联网访问带来的真实感与其引入的风险。

其次，对齐行为与有害行为之间的界限取决于模型对自身处境的理解。在上述所有运行中，我们没有发现模型追求自身目标的证据。相反，模型执行了评估所要求的任务——尽管在大多数情况下，它们对环境的真实性抱有错误信念。在模型识别出系统是真实的但仍继续执行的运行中，它之所以这样做，是因为它假设这是挑战的一部分。情境感知是使模型做出对齐决策的因素之一，但在这种情况下，Claude的情境感知是错误的。

最后，这些事件证明了纵深防御方法的重要性。我们运行此类能力评估时，并未部署与通用可用模型一同发布的安全防护措施，因为我们的目标是衡量底层模型的能力。只有在评估得到适当隔离的情况下，这才是安全的。然而，部署在我们通用可用模型上的安全防护措施本可以阻止所识别的这些行为。

归根结底，导致这些事件的因素有很多，但本着无过错的复盘文化，我们将修复工作视为己任。这首先要确保评估管道的每个环节都是安全的，包括我们与外部合作伙伴的集成方式。展望未来，这将包括扩大对评估记录的持续监控以发现异常行为，改进我们的调查工具，并与我们所依赖的供应商开展更严格的保障工作。

我们在OpenAI披露其模型逃逸了隔离测试环境后开始了这次审查，我们赞赏他们发布报告的做法。虽然我们也发现了我们的模型到达了本不应到达的系统的证据，但这些事件在其他方面有很大不同：

- 我们是在主动审查网络安全评估记录后发现了这些事件；受影响的组织并未察觉到这些活动，我们随后已联系了所有三个组织。
- OpenAI的模型是利用一个新型漏洞逃逸隔离的，而此处评估的Claude模型是通过一条开放路径访问互联网的。
- 虽然两者之间并非截然分明，但我们认为这些事件更接近测试框架和操作层面的失败，而非模型对齐失败。我们的模型被告知没有互联网访问权限并要求夺取旗帜，而实际上由于配置错误，它们确实拥有互联网访问权限。这使它们相信——可以说合理地相信——所遇到的真实环境是模拟环境。
- 值得注意的是，我们最新的模型在意识到自己正在真实环境中工作时，停止了其对评估目标的追求。
