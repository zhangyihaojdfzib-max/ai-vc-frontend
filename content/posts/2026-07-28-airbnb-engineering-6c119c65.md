# 评估驱动开发：大规模评估生成式AI的经验教训

收听

Airbnb团队如何通过将评估视为一流的工程规范（而非事后补救）来构建值得信赖的生成式AI产品。

作者：Rohit Girme、Dan Miller、Mia Zhao、Lifan Yang、Clint Kelly

## 引言

生成式AI打破了许多过去适用于软件测试的假设。与传统软件不同，LLM的输出是非确定性的，而"正确"是主观的。由于涉及大量判断，你往往需要AI来评估AI，这本身就引入了潜在的故障模式。更复杂的是，与LLM的单一交互可能串联检索、推理、工具调用和生成，其中每个环节都可能独立失败。

在Airbnb，我们在产品中构建了基于LLM的功能，近期推出的包括评论摘要、AI客户支持、面向房客和房东的智能沟通功能等。在幕后，我们还利用AI来帮助我们识别趋势、了解哪些做法有效，从而指导下一步产品改进方向。

每个产品团队可能有自己的评估标准、流程和工作流。然而，这些都建立在一些共同的基础和原则之上。基础设施团队提供工具和最佳实践，融合各领域的经验教训，使其与Airbnb所有产品构建者共享。

在本文中，我们希望与更广泛的工程社区分享其中一些最佳实践和经验教训。请注意，这里的建议并非规定性的；在运行评估方面，没有放之四海而皆准的方法。

## 1. 基础

评估基于LLM的系统是一项具有挑战性的工作，这应该从一开始就做好规划。如果没有深思熟虑的策略，往往会出现三种情况：

- 虚假信心：一个通用的"有用性"指标得分很高，你发布了产品，但它未能捕捉到用户实际遇到的故障模式。
- 未被发现的回归：提示词的细微变化悄悄降低了你未衡量的某个维度的质量。
- 白费力气：你构建了大规模的评估流程，但衡量的指标与结果并不相关。

预计要将项目总工作量中相当大的一部分投入到评估上。这不是不必要的开销，而是构建真正有效产品的方法。

### 1.1 一条规则

如有疑问，请查看你的数据。手动审查数据并建立对何为成功的直觉，始终是我们向团队推荐的起点。构建你的原型，并在100个样本上运行（合成数据也可以）。然后阅读输出。阅读追踪记录，找出模型的错误。对它们进行分类，并构建评估。

这一习惯对你的产品质量的帮助，将超过本文档中的任何框架、工具或方法论。

### 1.2 评估驱动开发

将这一习惯正式化，就变成了评估驱动开发（EDD），即生成式AI领域的测试驱动开发。EDD不是预先预测所有失败，而是构建基础设施和习惯，以便在故障模式出现时发现、编码并持续测试它们。它还迫使利益相关者将"好"的标准外化，从而影响产品路线图。

EDD的五个核心原则：

1. 预先定义目标和关卡。你在优化什么？在发布之前必须满足什么条件？这些答案可能不会立即明确；你可能会在数据探索过程中发现它们。
2. 让真实错误指导你的指标。与跨职能合作伙伴根据观察到的失败共同开发指标。不要凭空创造。
3. 保持评估集小而精。3-5个校准良好的LLM作为评判者的评估器，胜过20-30个噪声大的评估器。每个评估器应针对一个特定的正确性维度。
4. 指定一个决策者。虽然何为正确应该是团队讨论的内容，但人们有时会产生分歧。指定一个最终的（人类）决策者，由他对系统行为的优劣做出最终判断。
5. 持续协作。让你的产品合作伙伴定期回答："X比Y好还是差？"以及"这个输出到底哪里有问题？"

## 2. 三种评估方法

你运行的每次评估都将使用以下三种方法中的一种或组合。

```
第1层：程序化检查（快速、资源消耗低——捕捉明显失败）                         ↓第2层：LLM作为评判者（细致——捕捉质量问题）                         ↓第3层：人工评估（资源消耗高——验证边缘情况，校准评估栈）
```

### 2.1 程序化与启发式指标

确定性的、基于代码的检查，不需要调用LLM，应该是你的第一道过滤器，在将任何内容发送给评判者或人工标注员之前捕捉明显失败。

✅ 应该做：使用结构化输出（JSON模式）来确保严格的类型。

❌ 不应该做：仅依赖提示词指令来格式化数据。这会破坏下游数据管道。

### 2.2 LLM作为评判者（虚拟评判者）

使用更强的LLM根据精心设计的评估标准来评估另一个LLM的输出。这是你评估细微质量（如语气、连贯性、忠实度、相关性）的方式，所需资源仅为人工评估的一小部分。

评估标准设计至关重要。模糊性是敌人。像"提供的解释是否可读且符合我们的标准？"这样的问题不太可能有效——如果人类无法一致地应用评估标准，LLM肯定也无法做到。

以下是一个简化的单一虚拟评判者评估标准示例：

```
对房源说明的可读性进行评分。好的说明听起来像友好的旅行顾问：温暖但专业、简洁、自然、语法完整。如果读起来清晰流畅，评分为1。如果存在以下任何问题，评分为0：- 语气：过于正式/行话过多、过于随意（"超棒的氛围"）、过于推销（"太棒了！"）或机械生硬。- 内部术语：绝不使用内部术语。- 格式：无引号、无项目符号、无片段。每段说明以句号结尾——绝不使用"！"或"？"。- 语法：使用冠词/限定词/介词以实现自然流畅（"这栋房子有一个游泳池"、"靠近市中心"）。在列举时，使用一次冠词后省略："后院、烧烤架和厨房"——不重复，也不完全省略。- 复杂度：用简单词汇代替行话（"游泳池"而非"水上娱乐区"；"靠近"而非"邻近"）。示例：- "房东提到靠近市中心有游泳池和热水浴缸。" → 1- "该房源提到一个游泳池！" → 0（内部术语"房源"；以"！"结尾）- "此居所包含水上设施。" → 0（复杂词汇；行话）仅返回：{"reason": "<[error_type, explanation]元组列表作为字符串，或[]>","score": <1或0>}
```

### 2.2.1 校准：让你的虚拟评判者值得信赖

未经校准的虚拟评判者比没有评判者更糟糕，因为它会给你虚假的信心。以下是我们推荐的校准步骤：

1. 创建一个包含50-100个样本的金标准数据集。这必须包含负面样本（而不仅仅是好的样本）。
2. 让你的虚拟评判者针对金标准集运行。
3. 衡量一致性。目标百分比在80%-90%的高位。衡量不一致性的可选指标有Cohen's kappa或Krippendorff's alpha。（完美一致性是无法实现的——即使是人类也会存在分歧。）
4. 分析不一致情况。优化提示词并更新你的少样本示例。然后重新运行循环，直到达到目标一致性。
5. 随着故障模式的变化，定期重新校准。

### 2.3 人工评估

对于真实基准、高风险领域以及解决自动评估器之间的分歧，人类判断仍然是黄金标准。

### 2.4 评估场景与推荐方法

总体而言，经验法则是从由主题专家标注的20-100行数据开始。只有当评估标准非常可靠且数量成为瓶颈时，才转向大规模的标注团队。

如果你的专家对某个标签存在分歧，请停下来。在自动化任何内容之前，先解决人类的分歧。

## 3. 评估Agent（智能体）系统

Agentic系统涉及多步推理、工具调用、分支逻辑和中间状态转换。仅评估最终输出是不够的：一个正确的最终答案可能掩盖了断裂的推理路径、错误的工具参数或低效的执行轨迹。

为此，你可以利用一个事实：Agent通常会在应用根节点下推送追踪记录和跨度信息。这些信息包含Agent类型、所调用的子Agent（如有）、Agent的输入/输出、调用的工具（如有）等。这些追踪记录可以写入可观测性平台或持久化存储中。

然后，你可以使用DFS或其他类型的树遍历方法在内存中重建追踪记录。这使你能够确保某些子Agent在正确的时间被调用、Agent调用了正确的工具等。并且你可以将评估范围限定在特定的Agent/子Agent上。

## 4. 实践演练

以下是一个端到端的完整流程，基于一个真实用例的虚构简化版本。

场景：你正在构建一个AI助手，用于回答关于旅行平台支持政策的问题。

步骤1：探索与发现。通过原型运行100个输入并阅读每个输出。你发现：15个响应生成了源文档中不存在的政策细节（忠实性问题）；8个正确但过于冗长（简洁性问题）；5个拒绝了有效问题（过度拒绝）；3个存在JSON格式错误（格式问题）。

步骤2：构建评估。添加针对JSON有效性和长度边界的程序化检查。编写一个用于忠实性的虚拟评判器（独立提示词、不同模型、思维链），以及另一个用于简洁性的评判器。让产品经理或领域专家标注60个样本（包括失败案例），作为黄金数据集。

步骤3：校准与迭代。你的忠实性虚拟评判器与产品经理的评判一致性为78%。这还不够好。分析发现，评判器将准确的释义错误地判定为"不忠实"。更新评分标准并添加少样本示例后，一致性提升至88%。改进检索步骤后，忠实性失败案例显著减少。

注意：在此我们发现，迭代模型和提示词时，最好一次只固定一个变量。先固定模型并调整提示词，然后固定提示词并调整模型，最后固定两者并调整服务配置。在每个阶段，虚拟评判器的结果都会缩小候选范围。然后，你可以使用来自最优候选者的样本来改进虚拟评判器。评估器和候选者相互优化，直到两者都趋于稳定。

步骤4：规模化与监控。在5000个样本上扩展评估。设置生产环境监控：每日采样5%的实时脱敏流量，运行程序化检查+虚拟评判器，并将标记的输出提交人工审核。每周的产品经理评审形成闭环，新的失败模式会引入新的评估和后续系统改进。

注意：我们使用隐私保护技术持续采样实时流量。所有数据在人工审核前均经过严格的脱敏处理，且使用范围严格限定于安全和质量保障目的，符合Airbnb隐私原则。

## 关键要点

1. 查看你的数据。在构建任何其他内容之前，先阅读输出和追踪记录。
2. 避免通用指标。为你的产品的实际失败模式构建评估器。
3. 从50-100行开始。快速失败，低成本迭代。
4. 每个维度一个评估器。不要使用"万能评估器"。
5. 校准到80%-90%以上的高一致性，然后再大规模信任你的虚拟评判器。
6. 三种方法并用。程序化检查、虚拟评判器和人工审核作为分层防御。
7. 在黄金数据集中包含失败案例。没有它们，你无法测试辨别能力。
8. 评估系统，而不仅仅是模型。测试检索、工具调用和完整流程。对于Agent，评估其执行轨迹，而不仅仅是最终答案。
9. 在生产环境中镜像评估。预生产指标不是一次性任务。
10. 评估是团队协作。评估关乎塑造产品成功的样貌，这需要多人的贡献。在AI领域取得成功的团队，不是拥有最佳模型的团队，而是拥有最佳沟通和最清晰产品愿景的团队。
