AI让每个团队的员工都能比以往更快地构建应用程序。

但这种速度也正是让每位CISO夜不能寐的原因：任何员工都可以构建应用程序，将其部署到公共互联网上，并意外暴露内部工作或公司数据。

今天，我们推出新工具，让您轻松保持托管在Workers上的应用程序的私密性。您现在可以直接将Cloudflare Access应用于某个Worker或账户中的每个Worker，这样您的应用程序默认就在公司登录系统之后，无需依赖每个开发人员自行设置。

您现在可以：

- 在账户级别设置策略，确保所有预览和生产部署默认位于公司登录系统之后。
- 在单个应用程序上设置策略，确保与其关联的每个域都强制执行身份验证，无论其部署方式如何。
- 精确查看谁访问了您的应用程序。直接在代码中获取每个已认证用户的电子邮件、姓名和组——无需进行JWT（JSON Web令牌）验证。
- 部署一个内部平台，其中每个部署默认都是私有的。我们开源了一个示例：一个内部静态站点平台，其中部署的每个Worker都是私有的。

## Workers上的Access：工作原理

当您在Worker上启用Access时，Cloudflare会在任何请求到达您的应用程序代码之前强制执行身份验证。无论请求如何到达您的Worker——通过自定义域、路由、workers.dev子域还是预览URL——都不重要。只要Access开启，用户就必须先进行身份验证。

![BLOG-3405 2.png](/images/posts/101f36ebb0fd.jpg)

以前，您必须在主机名级别进行配置，这意味着需要在您的Worker可访问的每个域上设置Access策略。如果您想为Worker添加新的自定义域，需要先更新Access策略，否则该主机名将无需身份验证即可访问。现在，策略直接附加到Worker本身，因此与该Worker关联的任何域或URL都会自动受到保护。您可以选择保护范围：仅预览URL，或所有主机名。

如果设置为仅预览，则为该应用程序创建的每个预览URL——无论是workers.dev预览URL还是用于预览的自定义域——在您部署新版本时都将要求身份验证。如果设置为所有主机名，则与该Worker关联的每个域都受到保护——自定义域、路由、workers.dev子域和预览URL。

Access让您控制用户的身份验证方式。您可以连接现有的身份提供商，让员工使用他们已有的凭据登录，或将访问权限限制为特定的电子邮件地址、电子邮件域或组。对于Agent，您可以通过服务令牌授予访问权限。

在此处阅读Cloudflare Access for Workers文档了解更多信息。

## 默认保持账户中每个Worker的私密性

如果您的组织中有开发人员部署Workers，您不希望依赖每个人都记得启用Access。您希望默认就是私有的。

您可以在账户级别设置一次Access策略，那么账户中的每个Worker——无论是现有的还是未来的——从创建那一刻起就是私有的。

您可以选择策略覆盖范围：仅预览URL流量、所有生产流量，或两者兼有。如果您的生产Worker有意公开，但您绝不想暴露进行中的部署，那么仅预览模式就非常有用。

如果您不需要账户级默认设置，只想锁定某个特定的Worker，可以直接对该Worker应用Access。

## 查看谁在访问您的应用程序

当Access保护您的Worker时，您可以获取关于谁在发起每个请求的信息——他们的电子邮件、姓名和组——以便个性化他们看到的内容、强制执行权限或按用户记录活动。

这通过您Worker的上下文对象（ctx）实现。每个到达您Worker的请求都携带一个包含该请求元数据的ctx。当启用Access时，我们会将已认证用户的身份附加为ctx.access。然后，调用ctx.access.getIdentity()即可获取用户的电子邮件、姓名等信息。

以前，这意味着您需要自己验证JWT——解析令牌、验证签名并提取声明。现在，当您的Worker上启用Access时，每个已认证请求都包含ctx.access。

获取用户身份所需的全部代码如下：

```
export default {
  async fetch(request, env, ctx) {
    if (!ctx.access) {
      return new Response("Access required", { status: 403 });
    }

    const identity = await ctx.access.getIdentity();
    const email = identity?.email ?? "unknown";

    return new Response(`Hello, ${email}`);
  }
};
```

## 部署前在本地测试

我们展示了如何使用ctx.access.getIdentity()让您的Worker获取关于谁在发起请求的信息——他们的电子邮件、姓名和组。

您可以在使用wrangler dev进行本地开发时使用此功能。在wrangler.jsonc中添加一个access块来模拟已认证用户：

```
{
  "access": {
    "dev": {
      "aud": "my-app",
      "identity": { "email": "admin@company.com" }
    }
  }
}
```

您的Worker会通过ctx.access.getIdentity()获取该信息——返回的身份对象与生产环境中获取的格式相同。在配置中更换电子邮件即可测试不同用户。

这意味着您可以验证正确的内容是否显示给正确的用户，而无需每次更改后都部署并通过Access登录。

## 部署默认所有应用程序均为私有的内部平台

如果您管理一个员工可以原型设计和部署应用程序的内部平台，您需要每个应用程序都是私有的，而无需在每个应用程序上配置访问控制。

Workers for Platforms让您大规模部署Workers。每个Worker都位于一个命名空间内，该命名空间的所有流量都通过一个单一入口点：调度Worker。

在您的调度Worker上设置Access策略，通过它部署的每个Worker默认都是私有的。

## 建立在坚实的基础上

此功能得益于FL2——支撑Cloudflare边缘的新Rust模块化代理。Access是您应用程序的前门，因此传统上它在请求管道中所有Workers逻辑之前运行。但为了让Access应用程序能够针对单个Worker本身而非其主机名，Access需要知道给定请求将到达哪个Worker。因此，我们需要将Workers路由与Workers执行分离，并移动路由逻辑，使其能在Access之前运行。

在我们基于NGINX和Lua模块的旧FL1系统中，这种更改将是复杂且危险的。产品之间的交互可能很微妙，如果逻辑依赖于另一个产品修改的共享状态，将其移动到请求管道的更早阶段可能不安全。

FL2让这一切变得简单。其严格的模块系统将逻辑划分为定义明确、顺序一致的阶段，这些阶段静态声明其输入和输出。我们能够依靠编译器来揭示阶段间任何损坏的交互，并自信地逐步推进这次重构。
