调试隐私保护协议非常困难。Oblivious HTTP 涉及四个不同方之间的多个不同步骤，更不用说二进制 HTTP 编码以及分散在多份 RFC 草案中的细节了。我们将从每秒处理数百万次请求的 Oblivious HTTP 等协议运营中积累的经验，整合到了一个简洁干净的 CLI 工具中——今天我们将其开源。

我们将其命名为 `ourprivacy-client`，简称 `pvcli`。我们以 Apache-2.0 许可证发布它，并欢迎社区贡献。

下面是一行代码，它通过中继、网关和源服务器执行完整的 Oblivious HTTP 请求。如果你不明白这意味着什么，别担心，我们会在下文解释。

```
pvcli --ohttp \
   --first-hop https://relay-cloudflare.ohttp.info \
   --proxy https://gateway.ohttp.info \
   -X POST \
   --header "content-type: application/json" \
   --data '{"test":1}' \
   https://target.ohttp.info/anything
```

我们将解释为什么构建这个工具，并展示它有多么方便。

### 为什么隐私协议难以调试

让我们仔细看看我们创建 pvcli 的动机。随着时间的推移，隐私团队的产品套件和客户群不断增长。我们增加了隐私代理和隐私网关等产品，这些产品为苹果的 Private Relay、微软的 Edge Secure Network VPN、Flo Health 的匿名模式等提供支持。随之而来的是越来越多的特殊客户需求、领域知识和复杂性。结果，我们在开发和事件响应中遇到了越来越多的障碍。

为了具体说明这一点，让我们看看我们的一个产品如何实现 Oblivious HTTP（也称为 OHTTP）。首先，快速入门一下。OHTTP 为用户提供了一种隐私保证：没有人能同时知道谁发起了请求以及他们请求了什么。为了实现这一点，OHTTP 需要两个服务器，一个中继和一个网关，由两个不共谋的方运营。

下面是 OHTTP 的时序图，其中我们的客户拥有中继，Cloudflare 拥有网关。从高层次来看，OHTTP 可以分解为以下步骤：

1. 客户端从网关获取公钥。
2. 客户端加密请求并将其发送到中继。
3. 中继从加密请求中移除“客户端是谁”的信息，并将其发送到网关。
4. 网关解密请求，并将其发送到目标服务器。
5. 目标服务器处理请求，并将响应发送到网关。
6. 网关加密响应，并将其发送到中继。
7. 中继将加密的响应发送到客户端。
8. 客户端解密，并获取明文响应。

如你所见，这涉及相当多的来回通信：

![BLOG-3291-diagram.png](/images/posts/19f0844cea65.jpg)

在调试时，每一步都是我们必须考虑的潜在故障点！

特别是，我们在调试 OHTTP 时遇到了某些类型的问题。

- 客户要求提供从他们那边测试实时系统的方法，我们经常为客户特定的部署编写一次性的自定义客户端。
- 找出哪个步骤导致了问题非常耗时。根本原因是我们系统的错误还是客户系统的错误？
- 检查原始比特位既繁琐又极易出错。OHTTP 基于二进制 HTTP，这是一种二进制编码的 HTTP 请求。每当我们需要检查二进制编码时，我们都得费力地检查原始比特位。

因此，我们决定将所有隐私协议整合到一个工具中。它拥有一个用户已经熟悉的简洁界面，按顺序显示协议的每一个步骤，并且足够灵活以支持新的协议和架构。

为了了解这带来的不同，让我们看看一个 OHTTP 调试场景——使用 pvcli 之前和之后。

### 没有 pvcli 的调试

假设我们运营一个位于客户网关前面的 OHTTP 中继。客户要求我们用以下请求进行端到端测试：

```
POST /anything HTTP/1.1
Host: target.ohttp.info
Content-Type: application/json

{"test":1}
```

回想一下之前的 OHTTP 步骤。第一步是从网关获取公钥。我们使用 curl 从客户网关获取它，得到如下结果：

```

```

这是一个很大的十六进制二进制字符串。为了理解它，我们查看 OHTTP RFC 9458 §3 并手动解析：

- `0029` 是十进制的 41，表明这个公钥条目有 41 个字节。
- `55` 是公钥 ID。
- `0020` 标识了我们可以使用的非对称加密方法。在这种情况下，是 DHKEM(X25519, HKDF-SHA256)。
- `b9bb667e2230dc01c6d6cc047f94a1083beb185c63e50ec09f7692a5a0832540` 是公钥。
- `0004` 告诉我们后面跟着 4 个字节的对称加密 ID。
- `0001` 和 `0001` 标识了我们可以使用的对称加密方法：HKDF-SHA256 和 AES-128-GCM。

我们对二进制字符串中的每个公钥重复此过程。

接下来，我们参考 RFC 9292，将原始 HTTP 请求转换为二进制 HTTP。我们借助一些定制脚本手动构建二进制数据：

```
0204504f5354056874747073117461726765742e6f687474702e696e666f092f616e797468696e670c636f6e74656e742d74797065106170706c69636174696f6e2f6a736f6e0a757365722d6167656e740c6665727265742f302e312e30000a7b2274657374223a317d2000
```

我们验证每个字段：

- `02` 表示这是一个不定长请求
- `04504f5354` 是 POST
- `056874747073` 是 https
- `117461726765742e6f687474702e696e666f` 是 target.ohttp.info
- 以此类推

最后，我们构建一个包装 HTTP 请求，用于承载我们的 OHTTP 请求。为此，我们花更多时间编写另一个临时脚本，使用之前的公钥，按照 OHTTP 指定的方式加密二进制 HTTP 请求。我们创建一个头部，它是公钥 ID、非对称加密方法 ID 和对称加密方法 ID 的拼接。然后，我们拼接头部和加密后的二进制 HTTP 请求，得到：

```
5500200001000164f03cef18f625f1dcd9fb26aa802081196bd6d7ba225bf60d3ba65f4f669d59f22d4d37dfd1e45ac9d5097bd7d8e186576ebff850509b5708fe1dbe4c88a7b93b95d153ee203382979063603fb1759bcc41049ac40950f80564de9d45fe8aa4e24259e313da4768b469bbb03037b9b0c34ae5f1b65dea09b8d25f2d5bb4833b68d516a3b19f0265841d5f23a11e74a8d17a04b616e888dd60f147
```

我们将这些字节放入包装 HTTP 请求的正文中，并将其发送到我们的中继。我们收到一个响应。

```
malformed request
```

这是什么意思？我们联系客户，询问他们是否可以分享网关的日志。同时，我们仔细检查我们构建的比特位。解码后的公钥看起来没问题。二进制 HTTP 请求……哦！我们看到：

```
...0a 7b2274657374223a317d 20 00 <- 为便于阅读添加了空格
```

BHTTP 是长度前缀的。这意味着我们指定了一个长度（0x0a 是十进制的 10），然后跟着 10 个字节。但这里，后面跟着 11 个字节。在 00 之前多了一个 20。20 代表一个空格字符，所以我们在构建正文时一定不小心添加了它。我们移除多余的字符，重新发送，然后它成功了！

### 使用 pvcli 调试

使用 pvcli，所有这一切现在都只需一个命令：

```

    --first-hop https://relay-cloudflare.ohttp.info \
    --proxy https://gateway.ohttp.info \
    -X POST \
    --header "content-type: application/json" \
    --data '{"test":1}' \
    https://target.ohttp.info/anything
```

### pvcli能做什么

安装方法：

```
# 如果尚未安装rust，请先安装
curl https://sh.rustup.rs -sSf | sh
# 安装pvcli
cargo install --git https://github.com/cloudflareresearch/pvcli
```

pvcli从curl中汲取了大量灵感。我们设计时遵循"最小意外原则"。因此，许多参数与curl相同！尝试向我们的cdn-cgi端点发送一个快速GET请求：

```
pvcli https://cloudflare.com/cdn-cgi/trace
pvcli --http3 https://cloudflare.com/cdn-cgi/trace
```

如果你好奇底层发生了什么，可以使用`-v`获取详细日志：

```
# 更多日志
pvcli -v --http3 https://cloudflare.com/cdn-cgi/trace
# 更多日志
pvcli -vvv --http3 https://cloudflare.com/cdn-cgi/trace
```

现在，回到之前的OHTTP命令：使用`--ohttp`告诉pvcli构造一个OHTTP请求。将中继作为`--first-hop`传入，网关作为`--proxy`传入。目标将是一个回显服务器，这样你可以看到目标会看到什么。在这个命令中，我们使用来自`ohttp.info`的中继、网关和目标填充了参数。

```
pvcli -vvv --ohttp \
    --first-hop https://relay-cloudflare.ohttp.info \
    --proxy https://gateway.ohttp.info \
    -X POST \
    --header "content-type: application/json" \
    --data '{"test":1}' \
    https://target.ohttp.info/anything
# 以下为精简输出
```

我们遇到过很多情况，希望将标头传递给中继而不是目标。你可以通过`--first-hop-header`实现这一点：

```
pvcli -vvv --ohttp \
    --first-hop https://relay-cloudflare.ohttp.info \
    --first-hop-header "authorization: Bearer relay-token" \
    --proxy https://gateway.ohttp.info \
    -X POST \
    --header "content-type: application/json" \
    --data '{"test":1}' \
    https://target.ohttp.info/anything
```

类似地，我们也遇到过需要使用mTLS向中继进行身份验证的情况，以确保正确的客户端与正确的中继通信。为此，你可以使用`--first-hop-client`和`--first-hop-key`。

```
pvcli -vvv --ohttp \
    --first-hop https://relay-cloudflare.ohttp.info \
    --first-hop-client ./relay-client.pem \
    --first-hop-key ./relay-client.key \
    --proxy https://gateway.ohttp.info \
    -X POST \
    --header "content-type: application/json" \
    --data '{"test":1}' \
    https://target.ohttp.info/anything
```

而且它就这么简单。需要测试一个包含中继、网关、任意标头和mTLS的完整Oblivious HTTP请求？或者只通过网关发送请求？又或者只想查看OHTTP密钥配置？pvcli只需一条命令即可完成，包括调试功能。

### 为什么构建我们自己的工具？

已经存在一些优秀的OHTTP工具。Martin Thomson的Rust实现和Chris Wood的Go实现在我们几年前构建最初的OHTTP实现时提供了巨大帮助。但pvcli不仅仅专注于OHTTP。我们计划在工具中尽可能多地添加隐私保护协议。因此，虽然还有其他开源工具可用于调试OHTTP，但没有一个工具能将OHTTP、CONNECT代理、MASQUE和Privacy Pass（即将推出）整合在一起。

### 为pvcli做贡献

Oblivious HTTP是一个了不起的协议，我们非常希望看到你使用它。我们希望这个工具能帮助人们调试OHTTP并编写自己的OHTTP实现。

我们欢迎贡献！要开始，请克隆位于https://github.com/cloudflareresearch/pvcli的仓库，并提交拉取请求。

如果你正在寻找贡献方式，以下是我们待办事项列表中的一些内容。对于MASQUE，我们计划支持通过HTTP/3代理TCP，以及通过HTTP/2和HTTP/3代理UDP和/或IP。对于OHTTP，我们计划支持后量子密码学、添加时序/延迟信息、支持分块OHTTP以及改进日志记录。

如果你有兴趣使用Cloudflare的OHTTP中继和网关，请联系我们。
