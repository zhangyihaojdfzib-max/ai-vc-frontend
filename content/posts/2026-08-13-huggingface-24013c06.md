# 使用Strands Agents、LeRobot和Hugging Face Storage Buckets，在一个地方完成记录、训练和部署

本文介绍了Strands Robots中的流式数据循环，这是一个智能体循环，它记录机器人演示，通过直接从Hub读取数据进行训练，并将策略部署回硬件，整个过程中数据集始终保持相同的磁盘LeRobot格式。

你已经拥有一个能够记录演示并将其推送到Hugging Face Hub的智能体。现在你想持续运行这个循环：全天收集片段，在增长的数据集上训练策略，部署它，然后拉取下一批数据回来进行改进。运行一次这个循环，每个环节都能正常工作。但每天运行它，你就会开始为重复的字节传输付费。你上传的录音不断增长，每次训练运行在开始前都会将整个数据集复制到GPU，每个新的检查点在下一批录音返回时被发送出去。

本系列的第一篇文章介绍了Strands Robots，这是来自AWS的开源SDK（Apache 2.0），它将机器人抽象、仿真和LeRobot栈暴露为AgentTools，你可以将它们组合成一个单一的Strands智能体。该文章涵盖了Robot()工厂、在仿真中记录演示、运行策略，以及将相同的智能体代码部署到物理SO-101。该工厂根据机械臂、人形机器人、移动底座和机械手的注册表解析名称，因此本文中使用的SO-100只是众多受支持形态之一。机器人目录列出了工厂已知的所有机器人。LeRobot的数据集格式已被Hub上来自8,000多个发布者的超过90,000个数据集和模型使用（LeRobot项目脉搏）。Strands Robots的录音只是其中之一，因此任何为读取LeRobot数据而构建的工具都可以无需转换地读取它。如果你是Strands Robots的新手，请从那里开始；本文假设你已经完成了该设置。

那篇文章沿着一个方向跟踪了智能体循环，从Hub数据集到物理机器人。本文则沿着另一个方向跟踪数据，从第一帧记录回到部署的策略，通过Hugging Face Storage Buckets——一种可变的、非版本化的、基于Xet的对象存储仓库类型，于2026年3月发布。一个bucket与你的数据集仓库并排放置在相同的hf://命名空间中，并使用你已有的hfCLI，因此它成为工作层，在你记录数据的那天和训练数据的那天之间保存你的数据。

必须有人决定保留哪些片段、场景何时漂移得足够远需要重新记录、今天的批次是否足够用于训练，以及哪个检查点替换机械臂上的那个。在收集活动中，这些决策中的每一个都会出现数十次，而每一个决策都需要在发出下一个命令之前查看返回的内容。这就是智能体的工作。本文带你了解单个智能体内部的数据循环：将演示记录到Storage Bucket中，存储它以便每次同步只上传更改的字节，通过直接从Hub流式传输数据集而不是下载它来训练，并通过一个关键字参数更改将检查点部署回硬件。本文的可运行配套代码位于examples/notebooks/05_streaming_data_loop.ipynb。

## 你将构建什么

第一篇文章记录了数据集并将其推送到Hub，而你在这里构建的智能体则从自然语言提示词记录LeRobot数据集，将其同步到Storage Bucket中，并逐帧流式传输相同的数据集，实时解码相机视频，无需本地副本。你在写入它的同一进程中读回它：记录数据集的同一个Strands Robots Robot()流式传输它。然后，你训练好的检查点通过一个关键字参数更改部署到同一个Robot()，它在硬件上记录的演示返回到同一个bucket。

图1. 四个阶段共享一个后端。Robot("so100")通过共享的DatasetRecorder记录LeRobot数据集；sync_dataset_to_bucket(...)将其同步到Storage Bucket中；stream_dataset(...)通过Hub读回它，无需完整下载；训练好的检查点通过mode="real"部署到同一个Robot。磁盘格式保持与LeRobot写入时完全相同。

因为一个Robot()既记录数据集又读回它，所以收集数据和训练数据是同一对象上通过同一后端的两个方法。智能体决定运行一个片段并调用一个工具；然后滚动以机器人的控制频率进行，直到片段结束，训练好的策略产生每个动作。整个循环只需几行代码：

```python
from strands import Agent
from strands_robots import Robot

sim = Robot("so100")                 
agent = Agent(tools=[sim])


agent("Record a pick-the-cube demo and sync it to my-org/robot-fave.")


for batch in sim.stream_dataset("my-org/robot-fave/cube_pick", repo_type="bucket").dataloader(batch_size=64):
    ...

```

接下来是那个循环内部实际发生的事情，一步一步来。

## 先决条件

#### 最低要求（默认仿真路径）

- Python 3.12+，Linux或macOS（MuJoCo后端支持Apple Silicon）。
- 用于智能体推理的Strands兼容模型提供商。带有AWS凭证的Amazon Bedrock、Anthropic API、OpenAI或本地运行的Ollama。
- 带有数据集扩展的Strands Robots：uv pip install -U "strands-robots[sim-mujoco,lerobot]>=0.5.1"。lerobot扩展引入了LeRobot（>=0.6.1）、datasets、av和torchcodec，因此记录和视频解码无需进一步设置即可工作。请参阅安装指南。

就是这样。本文的每个阶段都在配备这三项的笔记本电脑上运行。运行的是循环，而不是可工作的策略：默认路径使用模拟策略，它记录有效的数据集但不是有用的数据集。

#### 高级（buckets、硬件、真实策略）

- 一个Hugging Face账户和具有写入权限的令牌，以及用于创建buckets和同步数据集的hfCLI：pip install -U "huggingface-hub>=1.6.0,<2.0.0"，然后hf auth login。
- 对于硬件路径：一对SO-101从属和主控设备，或任何其他LeRobot支持的机器人，校准文件位于~/.cache/huggingface/lerobot/calibration/下。
- 对于本地视觉-语言-动作（VLA）推理：NVIDIA GPU。对于大规模训练：从Hub读取的GPU集群。
- 要运行训练步骤：uv pip install "lerobot[training]"。记录和流式传输不需要它。如果你跳过它，trainer.train()返回错误结果而不是检查点。故障排除指南指出了该错误以及修复它的安装。

## 第1步 - 将演示记录到bucket中

你全天记录新的片段，每个片段都是相机帧和关节状态-动作遥测的连续运行。LeRobot将其写为一小组大文件，随着你的记录而增长。将它们推送到版本化的数据集仓库中，每次追加都会变成一次提交，每个修订版本都会被保留。收集则想要相反的效果：某个地方可以写入字节并就地覆盖它们。这就是Storage Bucket，它位于你的Hugging Face工作区内，并使用你已有的权限。无需配置身份和访问管理（IAM）角色，无需跨源资源共享（CORS）规则，也无需维护上传服务。

你的智能体以LeRobot在硬件上写入的相同格式记录LeRobot数据集。记录片段，然后将完成的数据集同步到bucket中。提示词要求使用模拟策略，这是一个无需训练模型即可产生关节动作的替代品，因此你可以在拥有可运行的检查点之前运行整个循环：

```python
from strands import Agent
from strands_robots import Robot, sync_dataset_to_bucket

sim = Robot("so100")                 
agent = Agent(tools=[sim])
```

agent(
    "创建一个包含so100机器人的世界，添加一个红色立方体和一个前置摄像头，"
    "开始录制（repo_id='local/cube_pick'，root='/tmp/cube_pick'，fps=30，"
    "overwrite=True，task='拿起红色立方体'），运行模拟策略"
    "60步，然后停止录制。"
)

sync_dataset_to_bucket("/tmp/cube_pick", "my-org/robot-fave")

```

同步操作写入`hf://buckets/{bucket}/{run_id}`，其中`run_id`默认为数据集目录名称。第3步中的流式读取也会命名运行：ID的前两段是bucket，其余部分是其中的路径。

sync_dataset_to_bucket(root, bucket, run_id=...)验证数据集并通过`hf` CLI同步，与录制生命周期解耦。如果你直接驱动一个开放的录制器，同样的能力也存在于`DatasetRecorder.sync_to_bucket(bucket, run_id=...)`，而`stop_recording(bucket=...)`在你停止活动录制时同步。Bucket是你全天写入的工作层；对于版本化的、已发布的工件，你仍然调用`push_to_hub()`。两者保持相同的格式。

片段在结构上是完整的，但动作是占位符，因此它不是你想要的那种训练数据。用`create_policy("<hf_repo>")`替换为真实策略以进行实际抓取；提示词、格式和bucket同步保持不变。

#### 在硬件上录制

要在物理SO-101上录制，LeRobot的录制CLI处理主从设备的启动：

```shell
lerobot-record \
  --robot.type=so101_follower --robot.id=my_follower \
  --teleop.type=so101_leader  --teleop.id=my_leader \
  --dataset.repo_id=my_user/cube_picking \
  --dataset.single_task='拿起红色立方体'

```

数据集以与模拟录制相同的格式落在磁盘上，因此相同的同步调用将其带到bucket：`sync_dataset_to_bucket("./recordings", "my-org/robot-fave", run_id="run-021")`（或它包装的`hf sync ./recordings hf://buckets/my-org/robot-fave/run-021` CLI）。采集运行追加到一个地方，你发布的仓库只包含你选择发布的版本。

## 第2步 - 使用字节级去重存储

现在数据集已在bucket中，问题是下一次同步的成本是多少。将两个固定摄像头对准一个清理同一张桌子的机械臂八小时，你录制的大部分内容都是你已有的像素：相同的光照、相同的底盘、相同的背景，跨越数千个片段。在版本化仓库上情况更糟，因为更改多GB视频分片中的一帧会重新上传整个文件。

Bucket由Xet支持，它使用内容定义的块级分块在字节级别对你的上传进行去重。块边界跟随内容，因此插入几个字节只会改变它所在的块，而不是移动之后的所有边界。在Hugging Face自己的测量中（HF存储），内容定义的块级分块将整个Hub的每次上传数据传输量减少了约四倍，企业计划的计费基于去重后的占用空间。他们的bucket基准测试展示了这在单个文件上的效果。从500 MB的上传开始，更改1%的字节并重新上传移动了5.5 MB，更改5%移动了27.5 MB，更改10%移动了55 MB。如果没有块级去重，覆盖一个对象意味着再次发送其所有字节，无论它们是否更改。

这能节省多少取决于文件布局，Strand Robots录制器使用LeRobot的布局。片段进入Parquet分片（data/chunk-000/file-000.parquet）和每摄像头MP4分片（videos/observation.images.front/chunk-000/file-000.mp4），仅在当前文件填满时滚动到新文件，使用LeRobot的默认值：数据Parquet为100 MB，视频MP4为200 MB。因此，一天录制后的同步上传新的尾部片段加上增长的部分填充片段，而不是整个数据集。明天再次同步同一个bucket，Xet处理去重。

![fig2_xet_dedup](/images/posts/951ce302b07a.png)

图2.同步只上传更改的内容。新数据集的首次同步上传每个块；录制更多片段后，Xet的内容定义块级分块意味着下一次同步只上传新块，跳过已存储的块。

## 第3步 - 通过从Hub流式传输进行训练

要训练，你将GPU指向数据集。先下载它会让GPU闲置，直到数百GB复制完成。由于第2步中的分片布局，直接从Hub流式传输在这里有效：一个批次变成对大型分片的几次字节范围读取，而不是数千次小获取。LeRobot的`StreamingLeRobotDataset`将其转换为即插即用的torch可迭代对象，Strand Robots通过`stream_dataset()`暴露它：

图3.流式传输，不要下载。下载路径先将整个数据集复制到本地磁盘，因此GPU等待；`stream_dataset()`直接从bucket读取批次，本地磁盘上什么都没有，因此GPU从第一批开始训练。

```python
reader = sim.stream_dataset("my-org/robot-fave/cube_pick", repo_type="bucket",
    shuffle=False, max_num_shards=1, buffer_size=1,  
)

print(reader.num_episodes, reader.num_frames, reader.fps)
for frame in reader:
    frame["observation.images.front"]   
    frame["observation.state"]           
    frame["action"]
    break

```

本地磁盘上只存放小的`meta/`文件夹，包含模式、统计数据和片段索引。摄像头帧在迭代时从远程MP4分片解码；状态和动作来自Parquet分片。该循环一次读取一帧，适合检查片段。要训练，将reader传递给`DataLoader`并迭代批次。流式数据集通过有界水库缓冲区在内部洗牌，因此视频解码在多个工作进程间并行化，训练步骤本身是普通的PyTorch：

```python

for batch in reader.dataloader(batch_size=64, num_workers=4):
    loss, _ = policy(batch)   
    loss.backward()

```

如果你完全不想编写循环，LeRobot自己的训练器通过相同的引擎读取，因此你的agent收集的数据集无需一行新代码即可训练。它通过进程内reader使用的相同关键字参数接受bucket：

```shell
lerobot-train --policy.type=act \
  --dataset.repo_id=my-org/robot-fave/cube_pick \
  --dataset.repo_type=bucket \
  --dataset.streaming=true \
  --num_workers=4

```

Bucket仅支持流式传输，因此`--dataset.repo_type=bucket`要求`--dataset.streaming=true`，配置否则拒绝该组合。当你想在自己的进程中拥有循环时，使用`stream_dataset()`：验证片段、在模拟中重放，或馈送自定义评估循环。对于仅本体感觉的流式传输，`drop_videos=True`完全跳过视频解码，这就是使其在没有`torchcodec` wheel的边缘设备上工作的原因。录制和数据集指南文档记录了该参数及其所需的`delta_timestamps`映射。

提供者名称在运行策略和训练策略之间共享。`create_trainer("lerobot_local")`返回一个类似`create_policy()`的`Trainer`，`TrainSpec`描述运行；记录-训练-部署循环然后在几行内闭合：

```python
import os
os.environ["STRANDS_TRUST_REMOTE_CODE"] = "1"   

from strands_robots import create_policy
from strands_robots.training import TrainSpec, create_trainer

trainer = create_trainer("lerobot_local", device="cuda")
spec = TrainSpec(dataset_root="/tmp/cube_pick", output_dir="/tmp/cube_pick_ft",
                 base_model="", steps=500, extra={"policy_type": "act"})
result = trainer.train(spec)                    
policy = create_policy(result.checkpoint_dir)   

```

在单个 NVIDIA L4（g6.4xlarge）上，对 120 帧片段执行 500 步优化器（ACT，51.6M 参数，有效批大小 8）在 133 秒内完成，并写入一个检查点，`create_policy()` 通过与运行任何其他策略相同的入口点加载该检查点。训练时间随数据集大小、批大小和步数扩展，因此请将此视为一个实测配置而非基准测试。“groot”和“cosmos3”提供程序针对相同的 `TrainSpec` 和 `Trainer` 生命周期，因此外围循环不变；每个提供程序首先验证其自身的必填字段，因此 GR00T 运行需要 `base_model` 和 `embodiment` 标签，而 Cosmos 3 运行需要 `base_model` 和 SFT 配方。在 `train()` 之前调用 `trainer.validate(spec)`，它会返回给定后端所缺失字段的精确列表。

Hugging Face 的预热缓存将数据分桶存储在靠近作业运行的云和区域边缘位置，因此您的集群进行本地读取，数据加载器保持领先于 GPU。在 Hugging Face 自身的桶基准测试中，在 `us-east-1` 区域的 `m5dn.24xlarge` 上测量，10 GB 负载的预热内容分发网络（CDN）读取命中约为 1,086 MB/s，而冷读取为 780 MB/s；100 GB 时预热读取约为 1,124 MB/s。与普通对象存储的完整对比（包括上传和下载）可在该仪表板上查看。选择数据存储位置是 Team 和 Enterprise 套餐中的“存储区域”设置，截至本文撰写时支持美国和欧盟，亚太地区和海湾合作委员会（GCC）区域已宣布即将推出；在这些套餐之外，存储库存储在美国。

在 macOS 上，`import strands_robots` 会自动将 Homebrew 的 `ffmpeg` 添加到加载器路径中，因此 `torchcodec` 无需额外设置即可解码流式视频。

## 第 4 步 - 部署策略并将数据返回循环

在此步骤中，您将使用刚训练的检查点在物理机器人上运行，并记录下一轮演示。这与第一篇文章中的智能体代码相同，仅将一个关键字参数改为 `mode="real"`：

```python
robot = Robot("so100", mode="real", port="/dev/ttyACM0",
              cameras={"front": {"type": "opencv", "index_or_path": "/dev/video0", "fps": 30}})
agent = Agent(tools=[robot])
agent("Pick up the red cube.")

```

检查点针对物理机械臂运行，该机械臂记录的演示以您最初使用的相同 LeRobot 格式保存到磁盘，准备同步回桶以进行下一次训练运行。

如果您的数据已存储在 Amazon Simple Storage Service（Amazon S3）上，本文中的格式工作均无需更改。LeRobotDataset 是 Parquet 和 MP4 分片的目录，因此它在 Amazon S3 上的存储方式与其他任何位置相同，录制、训练和部署步骤无论数据位于何处都读取该格式。桶新增的是 Hub 原生路径：`sync_dataset_to_bucket` 和 `stream_dataset(repo_type="bucket")` 直接以 `hf://` 为目标，因此您无需单独配置存储路径即可获得同步和流式读取。两条路径运行相同的循环：如果数据已存储在 Amazon S3 中则使用 S3；如果希望在无需预先配置存储的情况下获得同步和流式读取，则使用桶。

明天再次运行该循环时，您将录制到该桶中，仅同步更改的字节，并将这些字节流式传输到 GPU，无需等待下载。数据始终不离开 LeRobot 格式，也始终不离开 Hub。

## 使用示例应用程序试用

完整的 Strands Robots 示例位于 GitHub 上的 `strands-labs/robots` 仓库的 `examples/notebooks/05_streaming_data_loop.ipynb`。它逐单元引导您完成整个循环：录制、渲染、同步到桶、流式返回、训练和加载检查点。每个单元都在模拟环境中以模拟策略运行，因此无需 GPU、无需 Docker、也无需 Hugging Face 凭据。

```shell
git clone https://github.com/strands-labs/robots.git
